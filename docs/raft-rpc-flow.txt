 THE ONE-PARAGRAPH VERSION
   A Raft replica owns one poll thread and two rrr::Servers. Outbound RPCs go
   RaftServer -> RaftCommo -> RpcPeer -> rrr::Client -> ClientConnection ->
   TcpConnection, where they are BUFFERED, not sent. Inbound RPCs go
   TcpConnection -> ServerConnection -> generated dispatch -> RaftServiceImpl
   -> RaftServer. All actual socket I/O in both directions happens on the one
   poll thread. Requests are matched to replies by an integer `xid` held in a
   hashmap; requests are matched to handlers by an integer `rpc_id` held in a
   dispatch table. Those two tables are the whole correlation machinery.

      RaftServiceImpl -> RaftService -> rrr::Service        <-- WRONG

  Communicator declares exactly ONE virtual: its destructor. There are no
  virtual send methods. The base supplies connection lifecycle and peer
  LOOKUP; the derived class supplies every actual RPC. Base answers "who are
  my peers and how do I reach them"; RaftCommo answers "what do I say and what
  do I do with the reply".

  Frame is an ABSTRACT FACTORY producing three products -- CreateScheduler,
  CreateCommo, CreateRpcServices (frame.h:26-33). Frame::GetFrame(mode)
  (frame.cc:8-19) is the ONLY place a protocol name becomes a concrete type.
  Paxos is the symmetric sibling: PaxosServer/MultiPaxosCommo/
  MultiPaxosServiceImpl. MultiPaxosFrame additionally has CreateCoordinator
  (paxos/frame.cc:12), which is NOT on the base -- Paxos splits out a proposer
  object, Raft folds leadership into the server.

--------------------------------------------------------------------------------
 2.1 WHAT A FRAME IS
--------------------------------------------------------------------------------

  TCP gives you a byte stream with NO message boundaries. One read() may
  return one message, half a message, or two and a fragment. So rrr adds the
  boundary itself: a 4-byte length prefix.

      on the wire:   [len:4 native-order][payload ............]
                      ^^^^^                ^^^^^^^
                      framing layer        everything above it

  "A frame" = one complete message plus the length that lets you find its end.
  The frame layer never looks inside the payload.

  Three layers, each peeling one header:
      [len] [ payload ]                     TcpConnection's view
            [xid][rpc_id][args]             ServerConnection's view
                         [Raft fields]      RaftServiceImpl's view

--------------------------------------------------------------------------------
 2.2 TcpConnection's FIELDS -- everything that carries bytes
--------------------------------------------------------------------------------

  pub struct TcpConnection                                 tcp_channel.rs:79
    fd_                   : UnsafeCell<LegacyOwnedFd>   the socket
    outbound_             : Mutex<TcpOutBuf>            bytes awaiting write
    inbound_              : RefCell<FrameStreamReader>  bytes not yet a message
    pending_write_update_ : AtomicBool                  "I have bytes to flush"
    on_frame_             : Mutex<OnFrameCallback>      fires per COMPLETE frame
    on_closed_, on_error_ : Mutex<...>
    outbound_high_water_  : usize                       backpressure threshold
    poll_thread_          : Option<Arc<PollThread>>

  LOCKING, per the comment at tcp_channel.rs:81-85: outbound_ ALSO guards fd_
  (so a send cannot race a close), and on_frame_ gates inbound_. Separate
  mutexes were rejected because they grew the generated C++ object by 72 bytes
  and shifted every following field -- an ABI concern, since hand-written C++
  elsewhere depends on the layout.

--------------------------------------------------------------------------------
 2.3 THE TWO SHIMS -- how one socket faces two subsystems
--------------------------------------------------------------------------------

  TcpConnection implements NEITHER trait it needs. It has only an inherent
  `impl TcpConnection` at tcp_channel.rs:114 -- plain methods, no trait.

  In C++ you would write:
      class TcpConnection : public Pollable, public ChannelConnection
  But the DSL emits only SINGLE-trait inheritance: `#[cpp_inherit] impl Trait
  for Type` produces `struct Type : public Trait`, exactly one base.
  docs/porting-cpp-to-rust-dsl.md states the limit outright. This is a
  CONSTRAINT OF THE MIGRATION TARGET, not an aesthetic choice.

  So: two thin structs, each holding an Arc to the same connection, each
  implementing one trait, every method a one-line forward.

                      Arc<TcpConnection>            tcp_channel.rs:79
                      ^                          ^
         +------------+                          +------------+
         | conn_                            conn_             |
    TcpChannelShim    :238                  TcpPollableShim   :270
    impl ChannelConnectionBase :243         impl PollableBase :275
      send_frame, flush, close                fd, poll_mode,
      is_closed, peer_address                 handle_read, handle_write,
      set_on_frame/_closed/_error             handle_error, close,
                                              check_pending_write_update
         |                                                    |
         v                                                    v
    Box<dyn ChannelConnectionBase>          Box<dyn PollableBase>
      = ChannelConnectionProxy  channel.rs:95   = PollableProxy  pollable_proxy.rs:30
         |                                                    |
         v                                                    v
    the RPC layer                           PollThread::add_proxy(...)
    (ClientConnection or ServerConnection)  (the reactor owns it)

  TERMINOLOGY:
    POLLABLE = "epoll can watch me". It declares an fd and a poll_mode, and
               exposes handle_read/handle_write/handle_error callbacks. A
               two-way contract: the object says what to watch, the loop calls
               back into the object.
    SHIM     = a thin adapter between caller and callee that makes two
               interfaces fit, adding no logic. Both shims here are pure
               forwarding -- that is what makes them shims rather than layers.
    PROXY    = in rrr, `XxxProxy` is almost always just `Box<dyn XxxBase>`,
               i.e. an owning handle to an unknown implementor. NOT a network
               proxy. The exception is the generated RaftProxy/MultiPaxosProxy
               classes, which are RPC client STUBS.

  Same pattern for the listener:
      TcpListenerChannelShim  :565  -> ChannelListenerBase  :571
      TcpListenerPollableShim :605  -> PollableBase         :610
  And for services: ServiceBoxShim<T> (server.rs:231) holds a Box<T>.

--------------------------------------------------------------------------------
 2.4 THE THREE WAYS THE POLL THREAD GETS INVOLVED
--------------------------------------------------------------------------------

  (a) REGISTRATION -- once, at connect or accept. The real "enqueue".
        PollThread::add_proxy(&**pt, make_tcp_connection_pollable_proxy(...))
            connect path  tcp_channel.rs:1482
            accept path   tcp_channel.rs:1360
        epoll terms: EPOLL_CTL_ADD.

  (b) RE-ARM FROM ON the poll thread -- just an atomic flag.
        conn.pending_write_update_.store(true, Release)   tcp_channel.rs:837
        The loop checks check_pending_write_update() on its next sweep and
        re-arms the fd itself. No epoll call, no message.

  (c) RE-ARM FROM ANOTHER thread -- a cross-thread request.
        PollThread::update_mode(&**pt, conn.fd(), READ|WRITE)  :842
        This is NOT a syscall and NOT a registration. Look at reactor.rs:2162:
            self.sender_.send(PollCommand::UpdateMode { fd, new_mode })
        It posts an mpsc message. The poll thread picks it up next iteration
        and performs the real epoll_ctl (PollThreadWorker, reactor.rs:2059).
        epoll terms: EPOLL_CTL_MOD.

  (b) and (c) are the two branches at tcp_channel.rs:834-845. Both mean
  "please start watching for writable"; they differ only in how the message
  reaches the loop. Raft takes branch (b) almost always, because HeartbeatLoop
  is itself a fiber on the poll thread. The async-durability std::thread
  (server.cc:5737) is the real branch-(c) caller.

  IMPORTANT: interest is not readiness. update_mode says "tell me WHEN this
  becomes writable". The KERNEL reports readiness, later, via epoll_wait.

 3.5 (!) HOW THE SENDER LEARNS OF IT -- NOT BY AN EVENT
--------------------------------------------------------------------------------

   ###########################################################
   ##  NO EVENT EDGE. NO WAKEUP. NOTHING RESUMES ANYTHING.  ##
   ###########################################################

  AppendEntriesResponse::event EXISTS --
      created at commo.cc:41   response->event = create_sp_int_event(1)
      set     at commo.cc:17   response->event.as_ref().unwrap()->set(1)
  ...but NOTHING EVER CALLS wait() OR wait_timeout() ON IT. Those are the only
  two references in the whole tree. IT IS VESTIGIAL.

  What actually happens: up to 1 ms of nothing, then HeartbeatLoop's OWN
  TimeoutEvent fires, Reactor::run_loop swaps the fiber back in, and it POLLS
  the atomic:

      if (!resp.completed.load(std::memory_order_acquire)) { ...; continue; }
                                                            server.cc:4020
      Fiber::sleep(min(RESPONSE_POLL_STEP_US, remaining))   server.cc:4287
      RESPONSE_POLL_STEP_US = 1000                          server.cc:4000

  WHY -- the comment at server.cc:3996-3999 says it outright: wait_timeout on
  an individual response would PERMANENTLY mark that event TIMEOUT and lose a
  legitimate late persistence reply. Polling also gives every parallel RPC the
  same bounded round budget.

  DRAW THE REPLY AND THE RESUME AS DECOUPLED -- joined by an atomic flag and a
  ~1 ms polling tick, not by an arrow.

 4.4 THE TWO CORRELATION TABLES, TOGETHER
--------------------------------------------------------------------------------

    rpc_id ──► ctx.rpc_to_service ──► svc_index ──► ctx.services[i]

  Both are integers. Neither involves a search, reflection, or name lookup.
  The reply header carries NO rpc_id -- the client already knows what it
  asked; it only needs to know which outstanding request is being answered.

  rpc_id origin: rpcgen assigns it with random.randint(0x10000000,0x70000000)
  (rpcgen.py:334), then FREEZES it by reading the committed rcc_rpc.h back on
  every regeneration (load_existing_rpc_codes, rpcgen.py:291, called at :366).
  So the committed header IS the id registry. Renaming a method changes its
  id and is a WIRE BREAK, not a refactor.

1. YOUR OWN SERVICE IS NOT USED BY YOUR OWN REPLICATION.
   When you are leader, your commo talks to the FOLLOWERS' services. Your
   service sits idle until someone else is leader. commo and service are two
   halves of one conversation held by DIFFERENT MACHINES -- which is why
   following one node's code never walks you through both.

2. THE TRANSPORT ABSTRACTION IS DEAD ON THE PRODUCTION PATH.
   RaftTransport / TransportBase / RrrTransportAdapter / ChannelTransportAdapter
   are test-only.
     - make_rrr_transport has ONE reference: tests/raft_rrr_transport_compile_
       test.cc:17 takes its ADDRESS to force instantiation. Never called.
     - SendAppendEntriesCb (commo.cc:553) and BroadcastVoteCb (commo.cc:629)
       have callers only in rrr_transport.hpp:73, 93, 120. Zero live callers.
     - The only TransportProxy construction outside tests is
       test_cluster.hpp:144; test_cluster.hpp:10 self-describes as a SKELETON.
     - commo.h:462 mentions RrrTransportAdapter only inside a comment.
   Consequence: messages.hpp's 15 DSL structs have NO production consumer.
   commo.h:7 includes messages.hpp but neither commo.h nor commo.cc uses a
   type from it -- production uses RaftProxy::Rpc*Request instead (commo.cc:73,
   92, 162, 179, 227, 537, 595, 610, 658). See docs/raft-dsl-status.txt.

3. TWO DURABILITY SHAPES -- one reply arrow hides half the design.
     SYNC (default): follower fsyncs inline, reports followerAckType = Durable
                     on the ORDINARY reply. No second RPC.
     ASYNC:          follower replies Memory immediately; a TRACKED std::thread
                     fsyncs (spawned server.cc:5737, joined by the sweep at
                     :5726 -- NOT detached); then a SEPARATE
                     AppendEntriesDurable RPC goes out: server.cc:5783 ->
                     commo.cc:329 -> OnAppendEntriesDurable at server.cc:5006.

4. IN kSingleGroup MODE, stub servers spawn EXTRA poll threads whose
   RaftServiceImpl points at the SAME RaftServer (raft_main_helper.cc:353-390),
   each with its own thread-local Reactor. Inbound RPCs can land on a DIFFERENT
   poll thread than HeartbeatLoop. Only mtx_ makes that sound.

5. ServerConnection IS PER-CONNECTION, NOT PER-REQUEST, and is never freed
   early. on_closed (server.rs:1319) only calls close(); the Arc stays in
   Server::channel_sconns_field.conns until the Server itself is destroyed
   (the only clear() is at server.rs:851, in teardown). So upgrade() at
   rcc_rpc.h:1023 rarely returns None -- it usually upgrades to a CLOSED
   connection, and reply() on a closed one is a no-op. The Option guards the
   shutdown race, not the ordinary disconnect.

6. RaftProxy's synchronous AppendEntries (rcc_rpc.h:1428) and
   AppendEntriesTypedFuture::resolve() (:1396) are DEAD. Nothing outside
   rcc_rpc.h ever calls .resolve(). Raft is entirely async.

7. mtx_ BELONGS TO TxLogServer (scheduler.h:26), not RaftServer.
   RaftService HAS NO BASE CLASS (rcc_rpc.h:479).
   A "shim" here is not a code smell -- it is the sanctioned workaround for
   the DSL's single-trait inheritance limit (Part 2.3).

8. src/rrr/**/*.rs IS THE PRODUCTION SOURCE, transpiled by rusty-cpp. The C++

 PART 8 -- FIBERS AND THE POLL THREAD
================================================================================
 Added after a dedicated investigation of the Rust reactor. This part
 CORRECTS parts 2.4 and 2.5 above; where they disagree with this, this is
 the measured behaviour. Sources of truth are the Rust modules
 src/rrr/reactor/reactor.rs and src/rrr/reactor/fiber.rs, both schema-2
 canonical entries in src/rrr/rust-modules.toml (rrr.reactor :108-109,
 rrr.fiber :120-121). There is NO competing hand-written C++ Fiber class.

--------------------------------------------------------------------------------
 8.1 WHAT A FIBER IS -- THREE LAYERS, AND ONLY THE TOP IS RUST
--------------------------------------------------------------------------------

  A Fiber is a STACKFUL coroutine. Do not think "Rust class" -- think
  "Rust scheduling state bolted onto a C stack engine":

    Rust   struct Fiber            reactor.rs:847
             id / status_ / func_       scheduling state ONLY
             fiber_task_                RefCell<Option<Box<fiber_task_t>>>
             _pin (PhantomPinned)       the engine holds this address
    Rust   struct fiber_task_t     reactor.rs:793
             fn_ / yield_ / fib_        fib_ is srpc_fiber, BY VALUE
    C      struct srpc_fiber       src/rrr/reactor/srpc_fiber.h:71
             caller_ctx                 callee-saved regs of the RESUMER
             fiber_ctx                  callee-saved regs of the FIBER
             stack_mapping              the mmap'd stack
             state                      NEW/RUNNING/SUSPENDED/FINISHED

  THE CONTEXT SWITCH IS HAND-WRITTEN ASSEMBLY. Not ucontext, not
  setjmp/longjmp, not Boost.Context:

    fiber_swap_context(from, to)     fiber_context_x86_64.S:24-50
                                     fiber_context_aarch64.S
    saves rsp, a synthesized resume address, rbx, rbp, r12-r15 into
    *from; restores the same from *to; ends `jmp *%rax`.

  It is really assembled: enable_language(ASM) at CMakeLists.txt:123 and
  the reactor/*.S glob at src/rrr/CMakeLists.txt:14. srpc_fiber.h:19 warns
  that the struct field order IS the .S offset ABI -- do not reorder it.

  Each fiber gets its OWN 1 MiB stack plus a guard page:
    kDefaultStackBytes = 1usize << 20      reactor.rs:776
    mmap(...)                              srpc_fiber.c:41
    mprotect(mapping, page_sz, PROT_NONE)  srpc_fiber.c:46

  Finished fibers are NOT freed. The stack is recycled through a per-thread
  LIFO pool (available_fibers_) and munmap'd only at Reactor teardown.

  "Am I on a fiber" is one thread-local, sp_running_fiber_th_
  (reactor.rs:181), read by Fiber::current_fiber(). Do not confuse it with
  g_active_fiber (srpc_fiber.c:15), which is private to the C engine so its
  entry trampoline can find its own srpc_fiber.

--------------------------------------------------------------------------------
 8.2 CORRECTION TO 2.5 -- WHAT create_run ACTUALLY DOES
--------------------------------------------------------------------------------

  Part 2.5 says create_run "runs the body INLINE on the calling stack ...
  a nested stack frame, not a scheduling handoff." Half right:

    RIGHT  it is SYNCHRONOUS. The caller does not proceed until the body
           parks or finishes. It is not a handoff to a scheduler.
    WRONG  "on the calling stack" / "a nested stack frame". A fresh 1 MiB
           stack IS allocated and the CPU IS switched onto it. This is a
           nested CONTEXT SWITCH, not a nested frame.

  The chain, with the step 2.5 omits:

    Fiber::create_run(f)                      reactor.rs:889
      -> Fiber::create_run_impl                         :896
      -> fiber_create_run_impl                          :3031
      -> reactor_create_run_fiber_at_impl               :3135
           1  get-or-create fiber (from the pool)       :3137
           2  old = save_running_fiber()                :3142
           3  set_running_fiber(&fiber)                 :3145
           4  register_fiber -> fibers_ registry        :3148
           5  fiber.run() or continue_(); recycle if done  :3151-3164
           6  self_.run_loop(false, true)   <-- NOT IN 2.5   :3167
           7  restore_running_fiber(old)                :3170

  STEP 6 IS THE ONE THAT MATTERS. create_run drives a NESTED reactor loop
  on the way out. So calling create_run does not merely start a fiber -- it
  can resume OTHER fibers before it returns to you. Section 8.6 shows the
  bug this causes in raft today.

--------------------------------------------------------------------------------
 8.3 THE ONE BLOCKING PRIMITIVE -- EVERY PARK IS AN EVENT
--------------------------------------------------------------------------------

  There is exactly one way a fiber blocks: it waits on an EventPollable.
  Fiber::sleep is not special -- it is a timeout event:

    pub fn fiber_sleep(microseconds: u64) {          reactor.rs:3036
        if microseconds == 0u64 { return; }          // sleep(0) NEVER yields
        let x = create_sp_timeout_event(microseconds);
        (*x).wait();
    }

  and wait() is the universal yield point:

    fn event_wait_impl<W: EventCore>(ev: &W, timeout: u64) {
        reactor_verify(reactor_th.thread_id_.get()
                       == rusty::thread::current_id());   // owner thread only
        if ev.core_status().get() == DONE { return; }      // second use
        if ev.is_ready() {
            ev.core_status().set(DONE);                    // FAST PATH: no switch
        } else {
            let fiber = Fiber::current_fiber().unwrap();   // aborts off-fiber
            reactor_rc.waiting_events_.borrow_mut().push_back(ev);
            if ev.core_is_composite() {
                reactor_rc.composite_events_.borrow_mut().push_back(ev);
            }
            if timeout > 0 {
                ev.wakeup_time_.set(now + timeout);
                reactor_rc.timeout_events_.borrow_mut().push_back(ev);
            }
            *ev.wp_fiber_.borrow_mut() = Rc::<Fiber>::downgrade(&fiber);
            ev.core_status().set(WAIT);
            (*fiber).yield_();          // <-- control returns to run_loop
        }
    }

  THREE CONSEQUENCES YOU MUST KNOW:

  (a) IT IS ILLEGAL TO WAIT OFF A FIBER. reactor_verify(fiber_opt.is_some())
      hard-aborts. THIS is why raft guards with
      `Fiber::current_fiber().is_some()` before every conditional sleep --
      server.cc:2108, 2160, 3296, 6632; service.cc:395;
      replicated_db.cc:750. Those guards are not stylistic.

  (b) A READY EVENT COSTS NOTHING. The fast path marks DONE and returns
      with no context switch at all.

  (c) FIBER RESUMPTION IS OWNER-THREAD-ONLY, AND THE REASON IS Rc.
      event_test_impl guards the wake path, commenting: "upgrading the weak
      fiber ref mutates a plain (non-atomic) Rc strong count; doing this
      from a foreign thread races the owner's own Rc<Fiber> clones and
      corrupts the count." So the single-poll-thread design in
      raft_worker.cc:365 (CreateCommo gets svr_poll_thread_worker_.clone())
      is a CORRECTNESS CONSTRAINT of the fiber representation, not a
      performance choice.

  There is NO fiber ready-queue. Readiness is rediscovered by rescanning
  waiting_events_ / timeout_events_ / composite_events_
  (RefCell<VecDeque<...>>, reactor.rs:1398-1400) on every pass -- an O(n)
  linear scan. A parked fiber is reachable ONLY through the Weak<Fiber>
  stored inside the event it waits on.

  Composite events (WaitAll / WaitAny / QuorumEvent) go on the extra
  composite_events_ queue because they must be POLLED; the code comments
  that "regular RPC events self-notify". Quorum collection is therefore a
  first-class scheduler primitive.

--------------------------------------------------------------------------------
 8.4 CORRECTION TO 2.4 -- ONE ITERATION OF THE POLL LOOP, IN ORDER
--------------------------------------------------------------------------------

  A PollThread is exactly ONE OS thread (spawned at reactor.rs:3606) owning
  one epoll set and, through thread-local storage, exactly one Reactor
  (reactor_tls_get, :3059-3069). "The poll thread" and "the fiber universe"
  are the same object: one fiber registry, one fiber pool, one set of event
  queues, one running-fiber slot.

  pollworker_poll_loop, reactor.rs:3253-3368. Part 2.4 implied the command
  drain came first. It does not:

     1  jobs sweep #1                                        :3256
     2  epoll_wait, 1 ms timeout, max 100 events             :3263
     3  dispatch ready fds  (read / write / error)           :3266-3301
     4  drain the mpsc command queue (try_recv until Err)    :3304
     5  jobs sweep #2                                        :3305
     6  deferred fd removals                                 :3307
     7  jobs sweep #3                                        :3308
     8  THE FIBER + TIMER PASS  run_loop(false, true)        :3309
     9  pending-write re-arm sweep over every registered fd  :3315
    10  closed-pollable reap                                 :3337

  TWO ORDERING FACTS 2.4 GOT WRONG OR OMITTED:

    * A cross-thread PollCommand is picked up LATER IN THE SAME ITERATION
      (step 4), not "next iteration". epoll_wait's 1 ms timeout bounds the
      post-to-pickup delay -- UNLESS a fiber blocks in step 3 or step 8, in
      which case the delay is unbounded.
    * The pending-write atomic flag is consumed at step 9, i.e. AFTER the
      fiber pass at step 8. So a reply a fiber writes during step 8 gets its
      fd armed for writability in the SAME iteration. That ordering is
      load-bearing.

--------------------------------------------------------------------------------
 8.5 THE RPC PATH IN FIBER TERMS
--------------------------------------------------------------------------------

  INBOUND -- exactly TWO nested fibers per raft request:
    1  the generic dispatch fiber      src/rrr/rpc/server.rs:1523
    2  the rpcgen per-method wrapper   rcc_rpc.h:957, 986, 1021, 1058,
                                       1090, 1118, 1146, 1177, 1206, 1236
       (macros.h:69-74 generates the __Method__wrapper__ that calls
        Fiber::create_run)
  Two, not one, because raft's methods are registered with reg_rpc rather
  than reg_fast_rpc (the `fiber` IDL attribute; see Part 1).

  WHAT THE FIBER BUYS: the handler may PARK on a reactor event. It buys NO
  immunity from blocking syscalls -- see 8.6.

  OUTBOUND -- two different shapes, which is easy to get wrong:
    AppendEntries   NO event edge. Its IntEvent is vestigial. HeartbeatLoop
                    polls an atomic and ticks on a 1 ms Fiber::sleep
                    (server.cc:4020, :4287).
    Vote            DOES park, on a QuorumEvent (server.cc:4647), and is
                    resumed by the poll thread when the quorum is met.

  REPLIES cost ZERO fibers. The raft client uses bind_channel_direct, not
  the recv-loop-fiber path, so a reply is decoded inline on the poll
  thread; it resumes a waiting fiber by marking that fiber's event ready.

--------------------------------------------------------------------------------
 8.6 THE HAZARD: A YIELDING FIBER DOES NOT HOLD mtx_ AGAINST ITS PEERS
--------------------------------------------------------------------------------

  TxLogServer::mtx_ is a std::recursive_mutex (scheduler.h:26). A recursive
  mutex is owned per OS THREAD. All raft fibers share one OS thread.
  Therefore a fiber that yields while holding mtx_ does not deadlock its
  peers -- IT SILENTLY ADMITS THEM.

  THIS HAPPENS TODAY. server.cc:5925-5956, inside OnAppendEntries'
  piggybacked leadership-transfer branch:

      // ... mtx_ is held by `lock` here ...
      Fiber::create_run([this]() {        // server.cc:5934
          Fiber::sleep(30000);            // parks IMMEDIATELY
          if (!stop_.load(Acquire)) { RequestVote(); }
          transfer_election_jobs_.fetch_sub(1, AcqRel);
      });
      // ...
      lock.unlock();                      // server.cc:5956  <-- only HERE

  Sequence: the body parks at once, so create_run reaches its Step 6
  (run_loop, reactor.rs:3167) with mtx_ STILL HELD. That nested loop can
  resume another fiber -- an inbound handler, or HeartbeatLoop -- which
  re-acquires mtx_ recursively, succeeds because it is the same thread, and
  runs inside a critical section the first fiber believes it owns.

  Mutual exclusion between fibers is not actually provided by mtx_. Any
  invariant that assumes "I hold mtx_, therefore no other handler is
  midway through Raft state" is unsound across a yield.

  RULE TO ADOPT: never yield (Fiber::sleep, create_run, or any event wait)
  while holding mtx_. Where a delayed action is needed, capture what you
  need, unlock, then spawn.

  SECOND HAZARD, different in kind: a fiber that blocks in a real syscall
  stalls the ENTIRE poll thread, and with it every other fiber and every
  connection on that thread. Raft does this on purpose in synchronous
  persistence mode: OnAppendEntries fsyncs on the poll thread
  (server.cc:5832), and WaitForLogPersistenceTicket waits on a real
  condition variable. That is a throughput cliff, not a correctness bug,
  but it is invisible in fiber-level reasoning.

--------------------------------------------------------------------------------
 8.7 THE RAFT CONSENSUS DECISION, TOLD ONLY IN FIBERS
--------------------------------------------------------------------------------

  The thesis "you can build the Raft main logic by talking only about
  fibers" HOLDS -- for the consensus decision, and only for that. Election,
  log replication, and the commit rule are three long-lived fibers plus one
  short-lived fiber per inbound RPC, all on one OS thread, using three yield
  primitives: IntEvent::wait_timeout, QuorumEvent::wait_timeout, and
  Fiber::sleep. Restart/recovery is excluded here by request.

  THE FOLLOWER. Two fibers matter. The ELECTION TIMER fiber
  (created once in Setup, server.cc:2706) parks on an event with a timeout.
  When it wakes it does not campaign blindly: it re-reads the timestamp
  that inbound AppendEntries updates and asks the DSL predicate
  raft_server_election_timeout_has_fired whether enough time has passed
  with no contact. If a heartbeat landed while it slept, it re-parks. Every
  inbound AppendEntries runs on its own short-lived fiber pair (8.5), takes
  mtx_, appends, advances commitIndex, and returns -- so "a follower" is
  just: one sleeping timer fiber, plus a transient fiber per message.

  THE CANDIDATE. The timer fiber wakes, the predicate says yes, and it
  becomes the candidate by calling RequestVote on its own stack. It sends
  Vote RPCs and then parks on a QUORUM EVENT (server.cc:4647) -- the
  composite event from 8.3, polled rather than notified. Each arriving vote
  reply is decoded inline by the poll thread with no fiber of its own, and
  the quorum event's test flips ready when the count is reached. The poll
  thread's step-8 pass upgrades the Weak<Fiber> in that event and resumes
  the candidate exactly where it parked. Nothing else in the process moved.

  THE LEADER. The HEARTBEAT fiber (server.cc:2699) is the engine. Contrary
  to part 3.1's sketch, it does not Fiber::sleep between rounds -- it parks
  on an IntEvent with a timeout, so it can be woken EARLY: Start() ->
  RequestReplication (server.cc:5262) signals that event when a client
  submits, which is the push path. Each round it walks the followers,
  computes next_index from the DSL backoff predicates
  (raft_server_append_reject_can_halve and friends), and sends
  AppendEntries. Those sends have no event edge: the loop polls an atomic
  and ticks on a 1 ms Fiber::sleep (server.cc:4020, :4287). Replies land
  inline on the poll thread and advance match_index; the commit rule is
  then a pure computation over those indices -- raft_quorum_majority_count
  and raft_server_commit_index_clamp -- run by whichever fiber last
  observed the change.

  So the whole consensus decision is: ONE timer fiber that asks a question
  when it wakes, ONE heartbeat fiber that can be woken early, ONE transient
  fiber per inbound message, and a quorum event for the one place a fiber
  genuinely must wait for a majority.

  WHERE THE FIBER STORY IS NOT TRUE -- four seams, none of them restart:
    1  INGEST is a real OS thread. Client submissions arrive on
       RaftWorker::submit_thread_ (SubmitLoop, raft_worker.cc:1112) and
       cross into fiber-land only via the event Start()/RequestReplication
       signals.
    2  APPLY is a real OS thread. RaftServer::apply_thread_ (server.h:2670)
       drains committed entries into the state machine.
    3  DURABILITY BLOCKS THE THREAD. WaitForLogPersistenceTicket waits on a
       condition variable, called from HeartbeatLoop and from
       OnRequestVote while holding mtx_. During that wait the poll thread
       serves nothing.
    4  A LEADERSHIP-TRANSFER MONITOR is its own thread
       (server.cc:5115 region and timer_threads_, server.h:2195).

  And the correctness caveat from 8.6 must be read alongside this section:
  the narrative's implicit "one handler at a time under mtx_" is FALSE
  across any yield.
