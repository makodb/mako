 1.1 BUILD PORTABILITY  (28728363)

 The project could not configure on ANY CMake 4.x. Three values that rotate
 between CMake releases were hardcoded for one release:

   CMakeLists.txt:11        CMAKE_EXPERIMENTAL_CXX_IMPORT_STD was pinned to
                            451f2fe2-... , the CMake 3.30/3.31 token.
                            Inspecting the release binaries shows 4.0.3,
                            4.1.2 and 4.2.3 all use d0edc3af-... and none
                            accept 451f2fe2. Now selected by CMAKE_VERSION.
   src/rrr/CMakeLists.txt:622
                            CMake renamed its `import std;` BMI directory
                            (__cmake_cxx_std_23.dir -> __cmake_cxx23.dir in
                            4.2). Both spellings are now passed as
                            --runtime-module-root.
   scripts/check_rrr_crate_mode.py
                            resolve_prebuilt_module_dirs() skips a module
                            root this CMake did not create, and fails only
                            when none of the supplied roots exist. The
                            "unavailable" wording is retained deliberately:
                            scripts/tests/test_extract_rrr_rust.py pins it.

 This is a genuine portability defect independent of any host.

 1.2 THE ODR VIOLATION  (4e427f74)  -- TODO step 1

 log_storage.hpp and snapshot_manager.hpp each redeclared slotid_t and
 ballot_t behind #ifndef guards as UNSIGNED, while constants.h:6 spells
 ballot_t as SIGNED int64_t. Neither header included constants.h, so the
 type each declared depended on include order.

 Measured with clang -E using real compile_commands.json flags: of the 18
 TUs that transitively include either header, 16 saw constants.h first
 (signed) and 2 did not --

   tests/legacy_raft_log_test.cc            log_storage.hpp at .i line 99874,
                                            constants.h only at 160777
   tests/raft_memory_snapshot_manager_test.cc
                                            constants.h never included

 Both got ballot_t = uint64_t. The cause in the first is a two-line
 accident: line 8 includes log_storage.hpp, line 9 includes tpc_command.h
 which reaches constants.h via __dep__.h:120. Swapping those two source
 lines silently changed LogEntry::term's signedness, and the build uses -w
 so nothing warned.

 The consequence was a real ODR violation. server.cc.o and
 legacy_raft_log_test.cc.o both defined the weak comdat symbol
 janus::raft::LogEntry::load(BinaryReadArchive&) compiled against different
 field types; both were linked into build/test_legacy_raft_log and the
 linker kept one. Member types are not mangled, so nothing detected it.

 FIX: include ../constants.h, delete the guarded redeclarations.
 PROOF: the two LogEntry::load bodies are now byte-for-byte identical
 (84 instructions each, llvm-objdump). Before, they differed.

 1.3 PARAMETER REDUCTION  (84f1dea6)

 Five DSL predicates took an `invalid_site_id: u16` parameter for one
 reason: a Stage-1 carrier compiles under bare rustc with no --extern and
 no --type-map (scripts/raft_dsl.sh:329-331), so it could not read the
 INVALID_SITEID macro. The sentinel was threaded in from every call site to
 serve the tool, not to express anything about the domain.

 A DSL block can declare its own constant:

     pub const RAFT_SERVER_INVALID_SITE_ID: u16 = 65535u16;
  -> constexpr uint16_t RAFT_SERVER_INVALID_SITE_ID
         = static_cast<uint16_t>(65535);

   raft_server_site_is_preferred_leader          3 -> 2
   raft_server_vote_is_already_granted_to_other  5 -> 4
   raft_server_leader_hint_after_transition      5 -> 4
   raft_server_view_leader_locale                5 -> 4
   raft_server_recovery_leader_site              5 -> 4

 Baseline distribution across all 104 predicates in server.h:
   params  0   1   2   3   4   5   6   7
   count   1  17  41  21   8   9   4   3      mean 2.73, max 7

 A new static_assert pins RAFT_SERVER_INVALID_SITE_ID against
 static_cast<uint16_t>(INVALID_SITEID) so the DSL constant cannot drift
 from the macro it stands in for.

 21 call sites updated across server.{h,cc} and
 tests/raft_durability_accounting_test.cc.

 LIMIT OF THIS CHANGE, stated plainly: it removes parameters that were pure
 tool-workarounds. It does NOT make these methods. Turning
 f(site_id, preferred_site_id) into self.site_is_preferred_leader() means
 reading self.site_id_, which requires owning RaftServer, which requires
 the crate.

 4. WHAT IS STILL OPEN
--------------------------------------------------------------------------------

 4.1 BLOCKING QUESTION: can a ballot legitimately be negative?

 Production ballot_t is SIGNED int64_t. The already-DSL-owned RaftData at
 read_raft_disk.cc:57 spells the same six fields u64 (UNSIGNED). One is
 wrong. Answer requires finding where ballots are initialised and
 incremented and whether any sentinel is negative. Until answered, any
 conversion of a ballot-bearing type is a guess. This was step 2 of the
 removed TODO and is unchanged.

 4.2 THE ALIAS MACROS, still 29 #defines

 constants.h:6-29 remain preprocessor macros. A type map maps NAMES; a macro
 has already expanded by the time the compiler sees it, so this CANNOT be
 solved by the crate's type map -- it must be fixed in C++ first.
 Recommended order: convert the aliases raft uses, one per commit, full test
 matrix each time. Two specific traps:
   * bool_t (constants.h:26) is ON THE RPC WIRE (rcc_rpc.rpc uses it).
     Any change must leave generated rcc_rpc.h byte-identical.
   * key_t (constants.h:27) collides with POSIX <sys/types.h> key_t. The
     macro currently wins silently; a `using` turns that into a hard
     conflict. Handle last, alone.

 4.3 THE CRATE (the actual Stage 2 unlock) -- not started

 No raft Cargo.toml, no manifest, no type map. This is what makes impl,
 containers, rusty:: types and janus::Command expressible. Model on
 src/rrr/Cargo.toml, src/rrr/rust-modules.toml and
 src/rrr/rust-type-map.toml. Until it exists the DSL lane is free functions
 over scalars, and further scalar extraction does not converge on object
 ownership -- see 4.5.

 4.4 CHEAP WINS NOT YET TAKEN

   * RaftSubmissionProgress (server.h:1905, three bools) is the only cleanly
     convertible struct in server/service/frame. The STRUCT is Stage-1 legal
     today; only its impl needs the crate.
   * Ten orphan DSL functions have no caller at all (nine in server.h, one
     in commo.h, listed in docs/raft-dsl-examples.txt). Two more found here:
     raft_server_vote_is_already_granted_to_other has zero real callers, and
     raft_server_site_is_preferred_leader has exactly one (server.h:2433).
     The gate does not catch dead DSL.

 4.5 THE DIRECTION QUESTION, unresolved and important

 Stage 1 has moved LOGIC out of classes while the OBJECTS stayed C++: 104
 free predicates lifted from RaftServer, called 163 times, with zero impls
 anywhere in the 39 blocks. That is the inverse of the project's own
 doctrine --

   docs/porting-cpp-to-rust-dsl.md:191  "Core recipe: keep methods as
                                         methods, delegate gnarly bodies to
                                         free functions"
   docs/porting-cpp-to-rust-dsl.md:624  "This is *the* technique -- it
                                         carries ~80% of the migration.
                                         Call sites stay frozen."
   CLAUDE.md:190-191                     "a small @unsafe C++ kernel that
                                         the DSL body calls"

 In the doctrine a Rust method calls a C++ kernel. In raft today a C++
 method calls a Rust predicate. The arrow is reversed.

 src/rrr, which finished the migration, did it the doctrinal way: every
 module arrived object-shaped at its FIRST DSL commit (e.g. b6c0fd4f --
 class ConnectionMetrics became struct + impl + 38 methods + fields in one
 commit; 8 call sites changed, and only because Rust lacks overloading).
 rrr's inline era ran NO rustc at all -- scripts/rrr_dsl_check.sh is a
 sha256 drift guard. The first Rust compile arrived WITH the crate, two
 months after the objects had flipped.

 So raft's bare-rustc gate is not the regime rrr succeeded under. It is the
 strongest verification in the repo AND the thing that forces objects to
 stay in C++. Resolving that tension is a decision for the project, not a
 refactor: either the crate lands (restoring rrr's regime) or the gate is
 deliberately relaxed. Adding more scalar predicates in the meantime
 increases call-site churn that object ownership later reverses.
