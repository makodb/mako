# Marshal Archive Refactor — Design

Context: Workstream N. Replace the current `Marshallable` + `MarshallDeputy` + `Marshal` + `MarshallableProxy` design with a serde / cereal-style architecture that decouples **format** (how bytes are laid out) from **target** (where bytes go).

## Problem statement

The current `marshal.{hpp,cpp}` design has three issues:

1. **Buffer / fd / sink coupling**. `Marshal` itself is a memory buffer that exposes `write_to_fd(int fd, size_t)` as a member. Conflating "I am a buffer of bytes" with "I know how to drain myself to an fd" prevents reuse — to send bytes over a TCP socket or hash them into a digest, callers either copy the bytes through Marshal first or implement a parallel path.
2. **Redundant `pro::proxy` over virtual dispatch**. `Marshallable` is already an abstract base class with virtual `to_marshal` / `from_marshal`. Wrapping it in `pro::proxy<MarshallableFacade>` adds a second type-erasure layer with `MarshallableSharedPtrAdapter`, six `PRO_DEF_MEM_DISPATCH` macros, and a `MarshallableFacade::add_convention<MarshallableMemInner, std::shared_ptr<Marshallable>() const>` whose only job is to retrieve the same `shared_ptr<Marshallable>` you started with. `MarshallDeputy` then mirrors the same data in two fields (`sp_data_` proxy + `inner_sp_data_` shared_ptr).
3. **Save-and-load split.** Each command type writes a `to_marshal(Marshal&)` AND a `from_marshal(Marshal&)` — duplicate field-walking code per type. Cereal/serde collapse these into a single archive-templated `serialize` because the archive parameter is either an output archive (write side) or an input archive (read side); operator overloading dispatches at compile time.

## Reference designs

### Rust serde

Two traits, monomorphic per type, with **format ↔ target separation**:

```rust
trait Serialize {
    fn serialize<S: Serializer>(&self, ser: S) -> Result<S::Ok, S::Error>;
}
trait Deserialize<'de>: Sized {
    fn deserialize<D: Deserializer<'de>>(d: D) -> Result<Self, D::Error>;
}
```

The format library (bincode, JSON, MessagePack) provides the `Serializer` / `Deserializer`. The sink is anything implementing `std::io::Write` (file, socket, vec, gzip encoder, hasher, …). The user's `Serialize` impl is unchanged across formats and sinks.

Polymorphism over heterogeneous command sets is done via **tagged enums** (closed set, no boxing) or `Box<dyn Trait>` + a registry (open set, like mako).

### C++ cereal

Archive template, single-method save+load:

```cpp
struct MyType {
    int x; std::string y;
    template<class Archive>
    void serialize(Archive& ar) { ar(x, y); }
};
```

The archive is templated; `cereal::BinaryOutputArchive` writes to a `std::ostream`-shaped sink; `cereal::BinaryInputArchive` reads. `operator()` on the archive dispatches per primitive type. Polymorphism via `CEREAL_REGISTER_TYPE(MyClass)` + a string-keyed factory registry (same shape as mako's `MarshallDeputy::reg_initializer`, just generated by macros).

## Target architecture

Four layers, each independently composable:

```
┌──────────────────────────────────────────────────────────┐
│ Layer 4: Serializable trait (pro::proxy)                 │
│   For runtime polymorphism over heterogeneous commands.  │
│   SerializableProxy holds a type-erased command +        │
│   dispatches `serialize(BinaryWriteArchive&)` + `kind()` │
└────────────────────────────┬─────────────────────────────┘
                             │
┌────────────────────────────▼─────────────────────────────┐
│ Layer 3: Archive (format encoder/decoder)                │
│   Binary{Write,Read}Archive — knows the wire format,     │
│   holds a Sink/Source, exposes operator<< / operator>>   │
│   for primitives + dispatches T::serialize<Archive>(...) │
└────────────────────────────┬─────────────────────────────┘
                             │
┌────────────────────────────▼─────────────────────────────┐
│ Layer 2: Sink / Source trait (pro::proxy)                │
│   SinkProxy:   void write(const void* p, size_t n)       │
│   SourceProxy: size_t read(void* p, size_t n)            │
└────────────────────────────┬─────────────────────────────┘
                             │
┌────────────────────────────▼─────────────────────────────┐
│ Layer 1: Concrete sinks/sources                          │
│   BufferSink, FdSink, TcpSink, HashSink, ...             │
│   BufferSource, FdSource, TcpSource, ...                 │
└──────────────────────────────────────────────────────────┘
```

### Layer 1: Concrete sinks and sources

```cpp
class BufferSink {
public:
    rusty::Vec<uint8_t> bytes;
    void write(const void* p, size_t n) {
        const auto* b = static_cast<const uint8_t*>(p);
        for (size_t i = 0; i < n; ++i) bytes.push(b[i]);
    }
};

class FdSink {
    int fd_;
public:
    explicit FdSink(int fd) : fd_(fd) {}
    void write(const void* p, size_t n) {
        // ::write(fd_, p, n) — handles short writes
    }
};

class TcpSink { /* SOCKET send loop */ };
class HashSink { /* updates blake3/sha256 etc. */ };

class BufferSource {
    rusty::Vec<uint8_t> bytes;
    size_t pos_ = 0;
public:
    size_t read(void* p, size_t n) { /* memcpy from bytes[pos_..pos_+n] */ }
};

class FdSource { /* ::read(fd_, p, n) */ };
class TcpSource { /* recv() loop */ };
```

### Layer 2: Sink / Source proxy facades

```cpp
PRO_DEF_MEM_DISPATCH(SinkMemWrite, write);
struct SinkFacade : pro::facade_builder
    ::add_convention<SinkMemWrite, void(const void*, size_t)>
    ::build {};
using SinkProxy = pro::proxy<SinkFacade>;

PRO_DEF_MEM_DISPATCH(SourceMemRead, read);
struct SourceFacade : pro::facade_builder
    ::add_convention<SourceMemRead, size_t(void*, size_t)>
    ::build {};
using SourceProxy = pro::proxy<SourceFacade>;
```

Wrapping any concrete sink/source in the proxy gives type-erased dispatch identical to passing a `dyn Write` in Rust.

### Layer 3: Archive (binary format, current wire layout)

```cpp
class BinaryWriteArchive {
    SinkProxy sink_;
public:
    explicit BinaryWriteArchive(SinkProxy sink) : sink_(std::move(sink)) {}

    // Primitives — byte-for-byte compatible with current Marshal wire format.
    BinaryWriteArchive& operator<<(uint8_t v);
    BinaryWriteArchive& operator<<(int8_t v);
    BinaryWriteArchive& operator<<(uint16_t v);  // little-endian
    BinaryWriteArchive& operator<<(int16_t v);
    BinaryWriteArchive& operator<<(uint32_t v);
    BinaryWriteArchive& operator<<(int32_t v);
    BinaryWriteArchive& operator<<(uint64_t v);
    BinaryWriteArchive& operator<<(int64_t v);
    BinaryWriteArchive& operator<<(double v);

    // Variable-length integer encoding (current `v32` / `v64`).
    BinaryWriteArchive& operator<<(srpc::v32 v);
    BinaryWriteArchive& operator<<(srpc::v64 v);

    // Variable-length byte sequences — length-prefix + payload.
    BinaryWriteArchive& operator<<(std::string_view s);
    BinaryWriteArchive& operator<<(const std::string& s);

    // Composite: dispatches to T::serialize<BinaryWriteArchive>(*this).
    template<class T>
    requires requires(const T& t, BinaryWriteArchive& ar) { t.serialize(ar); }
    BinaryWriteArchive& operator<<(const T& v) { v.serialize(*this); return *this; }

    // Standard containers — composes via primitive ops.
    template<class T> BinaryWriteArchive& operator<<(const rusty::Vec<T>& v);
    template<class T> BinaryWriteArchive& operator<<(const std::vector<T>& v);
    // ... unordered_set, set, map, unordered_map, list per current marshal.hpp.

    // Direct byte write for opaque buffers.
    void write_bytes(const void* p, size_t n) { sink_->write(p, n); }
};

class BinaryReadArchive {
    SourceProxy source_;
public:
    explicit BinaryReadArchive(SourceProxy source) : source_(std::move(source)) {}

    BinaryReadArchive& operator>>(uint8_t& v);
    // ... mirror of WriteArchive.

    template<class T>
    requires requires(T& t, BinaryReadArchive& ar) { t.serialize(ar); }
    BinaryReadArchive& operator>>(T& v) { v.serialize(*this); return *this; }
};
```

The archive is **non-templated** in the sink — it holds a `SinkProxy` which is type-erased at runtime. The cost is one virtual call per primitive write (negligible vs. the actual I/O).

The user's `serialize` method **is** templated on archive (so that `BinaryWriteArchive` and `BinaryReadArchive` both work) — this is cereal's pattern. The same body runs for both save and load via operator overloading.

### Layer 4: Serializable proxy (runtime polymorphism)

```cpp
PRO_DEF_MEM_DISPATCH(SerializableMemSave, save);
PRO_DEF_MEM_DISPATCH(SerializableMemLoad, load);
PRO_DEF_MEM_DISPATCH(SerializableMemKind, kind);
struct SerializableFacade : pro::facade_builder
    ::add_convention<SerializableMemSave, void(BinaryWriteArchive&) const>
    ::add_convention<SerializableMemLoad, void(BinaryReadArchive&)>
    ::add_convention<SerializableMemKind, int32_t() const>
    ::build {};
using SerializableProxy = pro::proxy<SerializableFacade>;
```

(Implementation note — Phase 2 split the original single `serialize`
template method into separate `save` / `load` overloads, matching the
operator<< / operator>> split between `BinaryWriteArchive` and
`BinaryReadArchive`. cereal's unified `serialize` only works because
its archive types share an `operator()` interface; with separate
operator<< / operator>> the symmetry breaks down. save+load is also
cereal's documented fallback for asymmetric round-trips and adds
zero per-call overhead.)

Open-set polymorphism (mako needs this for arbitrary command kinds) goes through this proxy + a factory registry indexed by `kind`:

```cpp
// At startup:
SerializableRegistry::reg<TpcCommitCmd>(KIND_TPC_COMMIT);

// Send side:
SerializableProxy proxy = make_serializable_proxy<TpcCommitCmd>(args...);
proxy->save(write_archive);   // encodes the payload only

// Receive side (the kind has been read from the wire by the framework):
SerializableProxy obj = SerializableRegistry::create(kind);
obj->load(read_archive);      // decodes the payload
```

For closed-set sites (where the codebase knows all the command types statically), a `std::variant<TpcCommitCmd, NoopCmd, ...>` + the BinaryArchive is more efficient (no virtual call) — but the open-set proxy is the canonical replacement for `MarshallDeputy`.

### User-defined types

Each command type provides a single template method:

```cpp
class TpcCommitCmd {
public:
    int64_t txn_id;
    rusty::Vec<KvPair> updates;

    template<class Archive>
    void serialize(Archive& ar) {
        ar << txn_id << updates;     // operator<< on WriteArchive,
                                     // operator>> on ReadArchive — same line!
    }

    int32_t kind() const { return KIND_TPC_COMMIT; }
};
```

For asymmetric save/load (rare but exists), split into two methods:

```cpp
void save(BinaryWriteArchive& ar) const { /* ... */ }
void load(BinaryReadArchive&  ar)       { /* ... */ }
```

## Wire format compatibility

**The byte layout must remain unchanged**. The current `Marshal::operator<<(int32_t)` writes 4 little-endian bytes; `BinaryWriteArchive::operator<<(int32_t)` does the same. Variable-length `v32`/`v64` use the existing varint encoding. Strings prepend a `v64` length followed by raw bytes. Containers prepend a `v64` length.

**Byte-for-byte test**: serialize a representative type via the old `Marshal` path AND the new `BinaryWriteArchive` path; assert the two byte buffers are identical. This guards every primitive and composite during the migration.

## Migration phases

Each phase is committable independently with full RPC-suite green:

### Phase 0 — Design + workstream entry (this commit)
- This document.
- Workstream N entry in `docs/TODO-srpc.md`.

### Phase 1 — New abstractions (parallel, no caller migration)
- `src/srpc/misc/marshal_archive.{hpp,cpp}` defines:
  - `SinkFacade` / `SinkProxy` and `SourceFacade` / `SourceProxy`
  - `BufferSink`, `FdSink`, `BufferSource`, `FdSource` (initial set)
  - `BinaryWriteArchive` and `BinaryReadArchive` covering all primitives + std/rusty containers currently supported by `Marshal`.
- `tests/rpc_marshal_archive_test.cc` verifying byte-for-byte compatibility with `Marshal` for every primitive + every container shape.
- Existing `Marshal` / `Marshallable` / `MarshallDeputy` untouched.

### Phase 2 — `Serializable` proxy + factory registry
- `SerializableFacade` / `SerializableProxy`.
- `SerializableRegistry::reg<T>(kind)` and `SerializableRegistry::get(kind)`.
- One canary command type (e.g. `EmptyCommand` from `tpc_command.hpp`) implements both the old `Marshallable` interface AND the new `serialize` method; tests verify the proxy path produces the same bytes as the old path.

### Phase 3 — RPC framework boundary
- The auto-generated `rcc_rpc.h` macros switch from emitting `Marshal` operator<< / >> calls to emitting `BinaryWriteArchive` / `BinaryReadArchive` calls. This is a generator change; affects the generated code only.
- `MarshallDeputy` rewritten in terms of `SerializableProxy` while keeping its public surface (the `MarshallDeputy(std::shared_ptr<Marshallable>)` ctor still works — internally constructs a `SerializableProxy` from the shared_ptr's pointee).

### Phase 4 — Per-command-type migrations
Migrate command types in batches by directory:
1. `deptran/classic/` (TPC commands)
2. `deptran/janus/` (Janus commands)
3. `deptran/raft/` (Raft commands — careful, persisted log format)
4. `deptran/copilot/`, `deptran/paxos/`, `deptran/rcc/`
5. Test fixtures + benchmark commands

Each migration:
- Adds a `template<Archive> void serialize(Archive&)` method to the type
- Removes the old `to_marshal` / `from_marshal` pair
- Verifies the wire format matches the old version (regression suite catches mismatch via the round-trip RPC tests)

### Phase 5 — Remove old infrastructure
After all command types migrate:
- Delete `class Marshallable`'s virtual `to_marshal` / `from_marshal` methods (keep the class as a tag base if anything depends on it; otherwise delete entirely).
- Delete `MarshallableProxy`, `MarshallableFacade`, `MarshallableSharedPtrAdapter`, the six `PRO_DEF_MEM_DISPATCH` macros tied to it, `make_marshallable_proxy`, `marshallable_proxy_inner`, `wrap_typed_marshallable`, `TypedMarshallableAdapter`.
- `MarshallDeputy` keeps its public surface but its internals are entirely the new system.
- `Marshal`'s `write_to_fd` is removed (callers compose `Marshal`-as-buffer + `FdSink`).

### Phase N — Sink/Source coverage
Add sinks/sources beyond the initial set as new transports come online (e.g. zero-copy sinks for io_uring, hash sinks for content addressing, etc.).

## What gets simpler

After Phase 5:
- Each command type has ONE serialize method instead of two (save + load).
- `MarshallDeputy` has one field instead of three (proxy + shared_ptr mirror + kind).
- `Marshal::write_to_fd` is gone — `BufferSink::bytes` + `FdSink` compose.
- Supporting a new transport (e.g. RDMA buffer) is a new Sink class — no new format code, no command-type changes.
- Format change (e.g. switching to LEB128 varints, or a JSON archive for debug dumps) is a new Archive class — no command-type changes.

## What stays unchanged

- `Marshal` (the byte buffer with operator<< / operator>>) keeps existing — used internally by `BufferSink` and as the `BufferSource` underlying buffer. The migration replaces direct uses of `Marshal` in command-type serialization with the new Archive API; `Marshal` itself remains a primitive byte buffer.
- The wire format (byte layout). Every existing wire-format test must continue to pass byte-for-byte through every phase.
- `MarshallDeputy`'s public API (its constructors and methods that external callers use). Internally it gets simpler, but the surface stays.
- The factory registry pattern (`reg_initializer<T>` + `get_initializer(kind)`) — kept; just renamed to `SerializableRegistry`.

## Out of scope

- Switching wire format. The migration preserves byte-for-byte compatibility.
- Removing `std::shared_ptr<Marshallable>` from public APIs (separate L6 work, blocked on the non-owning shared_ptr in `scheduler.cc:375` and the persisted log format in `LogEntry::command`).
- `rusty::Arc` adoption inside marshal — separate concern; can be layered later atop the new design without touching command-type serialization code.

## Risks

- **Wire format drift**. If any phase silently changes a primitive's encoding (e.g. forgets to wrap an int in `v32`), every persisted log + every running RPC silently breaks. Mitigation: byte-for-byte tests in Phase 1 + round-trip tests through the actual RPC framework before retiring the old path.
- **Compile-time bloat**. Templated archives instantiate per command-type × archive-pair. Reasonable for current numbers but should be monitored.
- **Header coupling**. Once command types use `template<Archive>`, they must `#include` the archive header where the template body is visible. If we extract the archive trait into its own light header (no `pro::proxy` or `Marshal` dependencies), this stays manageable.
- **`pro::proxy` move-only convention args**. The Sink/Source proxies pass primitive types in their convention signatures, so this isn't an issue here. The L5-channel concern (move-only callbacks through proxy) is independent.

## Estimated total LOC

- Phase 1: +600 LOC (new abstractions + tests)
- Phase 2: +300 LOC
- Phase 3: ~200 LOC delta in code generator
- Phase 4: ~50 LOC delta per command type × ~80 command types ≈ ~4000 LOC delta (mostly delete + condense)
- Phase 5: -800 LOC (removal of old infrastructure)

Net long-term: roughly LOC-neutral, with substantial deletion of redundant adapter / proxy machinery. Per-command-type code drops by ~50% (one serialize method instead of save+load pair).
