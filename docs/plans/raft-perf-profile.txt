 READ THIS AS:

 1. ENTRIES ARE LARGE. The typical Raft entry is about 280 KiB (p50 ≈ 286 KB,
    p90 ≈ 306 KB, p99 ≈ 322-330 KB). This is not one transaction; it is a batch
    of them. src/mako/sto/Transaction.cc:636-653 accumulates `large_batch_num`
    transactions (default 400, overridable with MAKO_BATCH_SIZE) into one
    StringAllocator buffer and flushes it as a single Raft entry.

 2. THE TAIL IS LONG AND RARE. Partitions 2 and 4 show single entries of 13 MB
    and 25 MB, and 20 entries in total exceeded 8 MiB. That is why their mean
    (391 KB, 345 KB) sits above their p99 (328 KB, 325 KB): a handful of
    multi-megabyte entries drag the mean and nothing else. Transaction.hh:87
    caps the buffer at MAX_ARRAY_SIZE_IN_BYTES = 50,380,812, and the flush
    trigger is "400 transactions OR 90% of the buffer", so an occasional very
    large entry is expected rather than anomalous.

 3. THE SUBMISSION RATE IS LOW. About 50 entries/sec per partition, ~300/sec
    aggregate. That is consistent with the transaction rate: 160,402 txn/sec
    divided by a 400-transaction batch is ~400 entries/sec, and the batch also
    flushes on size. Raft in Mako is a high-bandwidth, low-message-rate path:
    roughly 300 entries/sec at ~290 KB each, about 85 MB/s.

 4. RAFT'S OWN "BATCH" KNOB DOES ALMOST NOTHING HERE. The fourth argument of
    add_log_to_nc is not entry coalescing. It sets RaftWorker::batch_limit_
    (raft_worker.cc:710, last writer wins across every partition), which only
    bounds how many already-queued payloads SubmitLoop drains per acquisition
    of submit_mutex_ (raft_worker.cc:1135-1143); each drained payload still
    gets its own Submit() → RaftServer::Start() → its own Raft log slot
    (raft_worker.cc:1146-1148). Mako passes 400, but the producer is so much
    slower than the drain loop that the observed batch is 1.04. Real
    wire-level coalescing happens elsewhere, in the leader's AppendEntries
    path, bounded by MAKO_RAFT_APPEND_BATCH_MAX_ENTRIES (default 256,
    server.cc:553-560).

================================================================================
 WHAT THE HARNESS TAKES FROM THIS
================================================================================

 * --payload-bytes brackets 286208 (the p50): one much smaller, the profile
   value, one much larger. scripts/raft_perf/run_sweep.sh declares those in
   PAYLOAD_BYTES at the top of the file.
 * --rate is centred on ~300 entries/sec aggregate for the profile payload.
   Because the achievable rate is bandwidth-bound, the offered-rate array has
   to be chosen per payload size; run_sweep.sh declares one array per payload.
 * --batch is swept over 1 and 400 (Mako's value), knowing from (4) that the
   expected effect is small. Measuring "small" is a result.
 * The harness does NOT try to reproduce the multi-megabyte tail. Entry size
   is a knob there, and a 25 MB entry is a rare event, not a workload.

================================================================================
 HOW IT WAS MEASURED, AND WHY NONE OF IT IS IN THE TREE
================================================================================

 Temporary lock-free histograms were added to src/deptran/raft/raft_worker.cc:

   * RaftWorker::EnqueueLog — one sample per call: the byte length, bucketed
     into 1 KiB buckets over 0..8 MiB plus an overflow bucket, together with a
     running sum, a running max, a first/last steady_clock timestamp per
     partition (for the rate) and an overflow counter.
   * RaftWorker::SubmitLoop — one sample per formed batch, taken after the
     drain loop and before submit_mutex_ is released: the aggregate batch size,
     the per-partition share of that batch (a batch can mix partitions when one
     worker handles all of them), and the effective limit.

 Atomics rather than locks, so the instrument does not reshape what it
 measures. The dump runs every five seconds from a detached thread and again
 from an atexit hook, because examples/test_1shard_replication_raft.sh ends the
 run with SIGTERM and then SIGKILL — an atexit hook alone never fires, which
 cost one wasted run before the periodic dump was added.

 The instrumentation was REMOVED after this measurement. `git diff` on
 src/deptran/raft/raft_worker.cc is empty; nothing about it was committed. To
 repeat the measurement, re-add equivalent counters at those two points, and
 note that the entry-size histogram must reach at least 8 MiB — an earlier
 128 KiB ceiling reported every percentile as the overflow bucket and produced
 a profile that said only "everything is bigger than this".

================================================================================
 CAVEATS
================================================================================

 * CLAUDE.md mandates running tests through Docker. Docker is not installed on
   this host (`docker info` fails), so this run was done directly on the host.
   The numbers are therefore not CPU-throttled the way ci/ runs are; the
   absolute rate would be lower under the CI cap. The SHAPE — large entries,
   low entry rate, batch of 1 — is a property of the workload, not the host.
 * The build logs at DEBUG (LOG_LEVEL_AS_DEBUG). That suppresses the absolute
   throughput and therefore the submission rate; the entry SIZE distribution is
   unaffected. raft_bench itself lowers the level to WARN by default for
   exactly this reason.
 * Followers were not profiled: they apply, they do not enqueue.
 * One run, not three. This is a calibration note for choosing payload sizes,
   not a measurement that anything is compared against; the harness itself
   repeats every point (scripts/raft_perf/run_sweep.sh TRIALS).
