================================================================================
 1. WHY NOT JUST USE dbtest
================================================================================

 ./build/dbtest prints agg_persist_throughput and friends, and it does drive
 Raft. It is still the wrong instrument, for two reasons.

 It measures the wrong thing. src/mako/benchmarks/bench.cc:677 computes
 agg_persist_throughput as n_commits / elapsed_sec, where n_commits counts
 TRANSACTIONS. Raft sits below Masstree, below the STO concurrency control,
 below transaction execution. A change in Raft moves that number by an
 amount swamped by everything above it.

 It cannot vary the inputs that matter. Entry size, batch size, offered
 rate, partition count and replica count are all consequences of the
 transaction workload in dbtest, not knobs. A performance harness needs them
 independent.

 dbtest keeps exactly two jobs in this plan: a one-time calibration source
 (step 1) and an occasional end-to-end cross-check that the standalone
 numbers are not lying (section 12, out of scope for now).

 2. THE THREE SOURCES, AND WHAT COMES FROM EACH
================================================================================

 FROM MAKO, reused as-is:
   * The replication bring-up API in src/deptran/replication_helper.h. This
     is the whole reason the driver is small. See section 5.
   * Topology configs. config/1leader_2followers/ already holds
     raft{N}_shardidx{S}.yml for N in {1,2,3,4,6,8,12,16}, where N is BOTH
     the thread count and the partition count. Generated by
     raft_generator.py in that directory, which is Python-3 clean if you
     need other values.
   * The metric DEFINITIONS from bench.cc: throughput as count over elapsed,
     per-core division, average and tail latency. Copy the definitions. You
     CANNOT invoke them; see section 3.
   * The three-process launch shape from bash/shard.sh and
     examples/test_1shard_replication_raft.sh.

 FROM ~/jetpack, ported:
   * The sweep design, which is the most valuable single item. ae/local/run.sh
     holds concurrency arrays per protocol (Raft gets 24 points from 1 to
     2000), a fixed comparison point per protocol, a six-point Zipf sweep and
     a seven-point key-range sweep. That is accumulated judgment about where
     the interesting regions are, encoded as data.
   * The driver structure from the same file: phases, --quick, --dry-run,
     timestamped output directories.
   * The plots. data_processing/lattput.py draws median latency against
     throughput; data_processing/plot_raft.py draws a latency CDF. Mako has
     never had either.
   * data_processing/processing.py as the starting point for the parser,
     though you will change its input format; see step 4.

   ~/jetpack IS READ-ONLY. Read it with cat, sed and grep. Never write there,
   never git anything there. It is a sibling research repository (a plugin
   consensus protocol over Raft, CoPilot and Mencius) that shares Mako's
   Janus ancestry, which is why the config schemas match.

 NEITHER HAS, so you build it:
   * The driver. Jetpack measures a replicated key-value store end to end.
     Mako measures transactions. Nobody measures Raft.

 DO NOT reuse src/mako/benchmarks/runner.py or plotter.py. They are Python 2
 (xrange, execfile), inherited from the original Silo code, and will not run.
 plotter.py also plots only ops/sec against thread count, which is a scaling
 curve rather than the saturation curve you want.

 3. DECISIONS ALREADY MADE; DO NOT RE-LITIGATE THESE
================================================================================

 D1. THREE PROCESSES ON THE PRODUCTION BUILD, not an in-process cluster.
     Mirror bash/shard.sh: three invocations differing only in -P, with the
     values localhost, p1 and p2. Rationale in section 11, trap T1.

 D2. COPY THE METRIC DEFINITIONS, DO NOT TRY TO INVOKE THEM. Mako's numbers
     are not a library. They are counters on the transaction hot path,
     arithmetic in the tail of bench.cc, and cerr prints. There is no
     function to call. Reimplement the same shapes over Raft events.

 D3. STRUCTURED OUTPUT, NOT LOG SCRAPING. Both Mako and Jetpack regex-parse
     log lines, which breaks silently. The driver writes one JSON object (or
     one CSV row) per run carrying every parameter and every metric. Adapt
     Jetpack's parser to read that. See step 4.

 D4. LATENCY BY EMBEDDED TIMESTAMP. Write the enqueue time into the payload
     and read it back in the apply callback. This is already proven in this
     codebase; see step 5.

 D5. PARTITION COUNTS 1 AND 6, AND BOTH GROUP MODES. One partition is the
     low-variance regression gate. Six is what production runs. The two
     group modes at six partitions bracket the cost of the shared recursive
     mutex. Do not sweep every partition count; three configurations is the
     agreed scope.

 D6. THE DRIVER LIVES AT src/deptran/raft/raft_bench.cc, beside the existing
     raft_lab_standalone.cc, with a CMake target added the same way.

================================================================================
 4. STEP 1: CAPTURE THE WORKLOAD PROFILE
================================================================================

 GOAL. Learn what Mako actually submits to Raft, so the synthetic payloads
 resemble it. Without this you will tune Raft against entries that do not
 occur.

 WHAT TO CAPTURE, per partition: the distribution of entry sizes in bytes,
 the distribution of batch sizes the submit thread forms, and the
 submission rate. Mean and the 50th, 90th and 99th percentiles are enough;
 you do not need full histograms.

 WHERE. The injection point is add_log_to_nc(const char*, int, uint32_t,
 int) declared in src/deptran/replication_helper.h; the fourth argument is
 the batch size. It routes to RaftWorker::EnqueueLog, which pushes onto
 submit_queue_, and RaftWorker::SubmitLoop drains it using
 raft_worker_batch_limit (src/deptran/raft/raft_worker.cc:67) to decide how
 many to coalesce. Instrument EnqueueLog and SubmitLoop with counters.

 HOW. Add temporary counters, run one replicated dbtest via
 examples/test_1shard_replication_raft.sh, print the summary at shutdown,
 then REMOVE the instrumentation before you commit anything. The profile is
 a note, not a code change.

 OUTPUT. Write the numbers into docs/plans/raft-perf-profile.txt with the
 exact command, the date, the commit and the workload used. Note that the
 profile is workload-dependent, so record which workload produced it.

 ACCEPTANCE. The profile file exists, names its provenance, and the
 instrumentation is gone from the working tree.

 5. STEP 2: THE DRIVER BINARY
================================================================================

 GOAL. src/deptran/raft/raft_bench.cc: bring up Raft, offer load, measure.

 THE TEMPLATE TO COPY FROM. src/mako/benchmarks/paxos_async_commit_test.cc
 already does bring-up outside dbtest, and it already measures latency by
 embedded timestamp. Read it first, lines 170 to 265. It shows:
   * building a char* argv by hand and calling setup(argc, argv), with -f for
     each config file, -P for the process name, -t for threads, plus -b -d
     -n -T -A;
   * register_leader_election_callback to learn when a leader exists;
   * register_for_leader_par_id_return per partition as the apply callback;
   * writing a start time into the payload and, in the callback, reading it
     back with std::stoll(std::string(log,16,16)) and subtracting to get a
     per-entry latency. Reuse this technique (D4).
 Its CMake registration is CMakeLists.txt:1534, add_apps(...). Its launcher
 is src/mako/benchmarks/paxos_async_commit_test.sh.

 THE API YOU NEED, all from src/deptran/replication_helper.h, namespace
 raft_impl (the unqualified names dispatch by replication type, which is set
 with --replication=raft):
   setup(argc, argv)                    bring the cluster up; returns
                                        hostnames, empty on failure
   setup2(action, shardIndex)           finish bring-up
   register_for_leader(cb, par_id)      apply callback on the leader
   register_for_follower(cb, par_id)    apply callback on a follower
   register_leader_election_callback(cb) leadership notification
   add_log_to_nc(buf, len, par_id, batch) INJECT HERE
   wait_for_submit(par_id)              drain
   get_outstanding_logs(par_id)         in-flight depth, for backpressure
   shutdown_paxos()                     tear down (the name is historical;
                                        it dispatches to Raft)

 WHAT THE DRIVER DOES.
   1. Parse its own arguments: --partitions, --payload-bytes, --batch,
      --rate (entries/sec, 0 meaning unthrottled), --duration-sec,
      --warmup-sec, --out <path>, --proc <localhost|p1|p2>, --config <file>,
      --group-mode <single|multi>, --label <string>.
   2. Build the replication argv and call setup then setup2, mirroring the
      template.
   3. Register an apply callback per partition. In it: read the embedded
      timestamp, compute the latency, record it, and count the entry.
   4. If this process is not the leader, do nothing but serve. Only the
      leader offers load. Use the leader-election callback to decide.
   5. Offer load: for --duration-sec, emit entries at --rate with
      --payload-bytes and --batch, stamping each with its enqueue time.
      Discard the first --warmup-sec of samples.
   6. Stop offering, wait_for_submit, then write the record (step 4) and
      shutdown_paxos.

 METRICS TO RECORD, per run: applied entries per second over the measured
 window; enqueue-to-apply latency mean and 50th, 90th, 99th and 99.9th
 percentiles; entries offered versus applied, so a shortfall is visible;
 peak get_outstanding_logs; and the run duration actually achieved. Keep
 raw latency samples in a preallocated vector and compute percentiles at the
 end; do not compute them online.

 ACCEPTANCE. Three processes launched by hand reach a leader, the leader
 applies what it offers, and one record is written. A run at --rate 0 should
 saturate; a run at a low --rate should show latency near the floor.

 7. STEP 4: STRUCTURED OUTPUT
================================================================================

 GOAL. Kill the regex-scraping failure mode before it starts (D3).

 FORMAT. One JSON object per run, written to --out. Include every input
 parameter and every metric, plus provenance: git commit, build flavour,
 hostname, date, the config file used, the group mode, and whether the build
 defined RAFT_TEST_CORO. A reader must be able to tell what produced the
 number without the surrounding directory.

 Suggested keys, flat, no nesting: commit, date, host, build_flavour,
 raft_test_coro, config, partitions, replicas, group_mode, payload_bytes,
 batch, offered_rate, duration_sec, warmup_sec, applied_per_sec,
 offered_total, applied_total, latency_mean_us, latency_p50_us,
 latency_p90_us, latency_p99_us, latency_p999_us, peak_outstanding, label.

 THE PARSER. Adapt ~/jetpack/data_processing/processing.py to read a
 directory of these records instead of parsing log text, and put it at
 scripts/raft_perf/processing.py. Keep its output shape, meaning whatever
 the plot scripts consume, so the plots port with minimal change.

 ACCEPTANCE. The parser turns a directory of records into the structure the
 plot scripts want, and a record with a missing key fails loudly rather than
 silently producing a wrong plot.

================================================================================
 8. STEP 5: THE SWEEP DRIVER
================================================================================

 GOAL. scripts/raft_perf/run_sweep.sh, ported from
 ~/jetpack/ae/local/run.sh.

 KEEP from Jetpack: the shape. Phase selection, --quick, --dry-run,
 timestamped output directory, the logging helpers, and above all the idea
 of holding the axis values in declared arrays at the top of the file rather
 than scattered through the logic.

 THE AXES for this harness, replacing Jetpack's protocol arrays:
   OFFERED_RATE   the saturation axis. Start from Jetpack's Raft concurrency
                  array shape, meaning dense at the low end and sparse at
                  the top, and translate it to entries per second using the
                  step-1 profile as the midpoint. Include 0, meaning
                  unthrottled, as the last point.
   PAYLOAD_BYTES  bracket the step-1 profile: at least the profile mean,
                  one much smaller and one much larger.
   BATCH          1 and the profile's typical value at minimum.
   PARTITIONS     1 and 6 (D5).
   GROUP_MODE     single and multi, at 6 partitions only (D5).
 A --quick run should be one point per axis, finishing in a few minutes.

 REPETITION. Each configuration runs at least three times and the parser
 reports the median with the spread. A single run is not a measurement.

 ACCEPTANCE. --dry-run prints the full matrix without running anything.
 --quick completes and produces parseable records. The full sweep's runtime
 is printed at the start so the operator knows what they started.

 11. TRAPS
================================================================================

 T1. DO NOT BUILD ON RaftLab. There is an existing five-replica harness at
     build_raftlab/deptran_server -f config/raft_lab_test.yml, and it is
     tempting because it is one process. It is compiled with RAFT_TEST_CORO,
     where the leader no-op is compiled out and the heartbeat interval is
     100 ms against production's 5 ms. Its numbers describe a different
     system. Use the production build (D1).

 T2. THE DSL. src/deptran/raft holds 26 inline Rust DSL blocks, marked
     '#if RUSTYCPP_RUST' with generated C++ between RUSTYCPP:GEN-BEGIN and
     GEN-END. If you edit a Rust block you must regenerate that carrier with
     third-party/rusty-cpp/target/release/rusty-cpp-transpiler inline-rust
     --rewrite --files <abs path>, run from the repo root. Never hand-edit a
     GEN region. Do not add new DSL items for this work; the driver is a new
     .cc file and needs none. Verify with bash scripts/raft_dsl.sh --check.

 T3. GROUP MODE IS THE LARGEST KNOB AND ITS DEFAULT IS SINGLE. CMake option
     SINGLE_RAFT_INSTANCE is ON, so RAFT_DEFAULT_SINGLE_GROUP is defined and
     the default is one Raft instance per process. In that mode the other
     partitions' ports are served by stub servers, each with its own poll
     thread, all dispatching into the same RaftServer behind one recursive
     mutex, so the mutex becomes genuine cross-thread contention. In
     per-partition mode each partition gets its own RaftServer and poll
     thread and there is no shared lock. Select with --raft-groups or
     MAKO_RAFT_GROUP_MODE=single|multi. Always record which mode produced a
     number.

 T4. PARTITION COUNT EQUALS THREAD COUNT in the generated configs, so
     raft6_shardidx0.yml means six partitions and six worker threads. You
     cannot vary them independently without regenerating configs.

 T5. LOOPBACK MEANS NO NETWORK LATENCY. The configs map localhost, p1 and p2
     all to 127.0.0.1. Three processes buy address-space isolation, not
     network delay. Every number from this harness understates replication
     latency for a geo-distributed deployment, and the documentation must say
     so.

 T6. THE APPLY CALLBACK RUNS ON THE APPLY THREAD, not the poll thread. Do
     not do heavy work in it and do not take locks that the poll thread
     holds. Record a sample and return.

 T7. shutdown_paxos IS THE RAFT SHUTDOWN. The name is historical; the
     unqualified replication_helper entry points dispatch on replication
     type. Do not go looking for a raft_shutdown.

 T8. THE THROUGHPUT KNOB THAT ALREADY EXISTS. Mako has CPU throttling with a
     CI test asserting throughput doubles when the cap doubles
     (ci/test_cpu_throttling_scaling.sh). If you need to vary capacity as
     well as offered load, use that rather than inventing a mechanism.

 WHAT STEP 1 FOUND, and what it changed about the plan's own assumptions

   Mako's Raft entries are much larger and much rarer than a reader of this
   plan would guess: a p50 of 286 KB, a tail to 25 MB, and only ~50 entries per
   second per partition (~300 aggregate across six). Each entry is a batch of
   ~400 transactions assembled by src/mako/sto/Transaction.cc, not one
   transaction. That set the payload axis (4 KiB / 286208 B / 1 MiB) and forced
   the offered-rate axis to be declared PER PAYLOAD, because the achievable
   rate is bandwidth-bound (~50-75 MB/s on this loopback) and no single array
   brackets the knee for both a 4 KB and a 1 MB entry.

   It also showed the plan's "--batch" axis measures less than it sounds like.
   The fourth argument of add_log_to_nc is not entry coalescing; it bounds how
   many queued payloads SubmitLoop drains per mutex acquisition. The observed
   batch is 1.04 whether Mako passes 1 or 400. That is recorded rather than
   assumed, and the axis was kept so the flat curve is evidence.

 VERIFIED ACCEPTANCE

   Step 2: three processes elect a leader, the leader applies what it offers,
           one record is written. --rate 0 saturates (1 partition, 4 KiB:
           ~11.9k entries/s); a low --rate sits near the floor (600/s ->
           2.76 ms p50).
   Step 3: one command, one record, no stray processes, run twice in a row.
   Step 4: the parser turns a directory of records into the plot input, and
           fails loudly with exit 1 on a missing key, malformed JSON, or an
           empty directory.
   Step 5: --dry-run prints the full matrix and the runtime estimate without
           running anything; --quick completes in ~2 minutes and produces
           parseable records.
   Step 6: both plots produce a PNG from a sweep's output, headless.
   T2:     bash scripts/raft_dsl.sh --check passes; no DSL item was added and
           no GEN region hand-edited.

 THE ONE CONFIGURATION THAT COULD NOT BE MEASURED

   D5 asks for both group modes at six partitions. Per-partition ("multi")
   group mode does not elect a leader above ONE partition on this tree: the
   three processes enter an unbounded election storm. Measured matrix —
   single/1 works, single/6 works, multi/1 works, multi/2 fails, multi/6 fails.

   Root cause, confirmed in source and independently by three reviewers:
   RaftServer::RequestVoteImpl passes the per-partition LOCALE id where a
   global SITE id is required.

     src/deptran/raft/server.cc:2733    const locid_t loc_id = loc_id_;
     src/deptran/raft/server.cc:2803-4  BroadcastVote(par_id, lst_idx,
                                            lst_term, loc_id, term)
     src/deptran/raft/commo.cc:112-117  that parameter is siteid_t self_id
     src/deptran/raft/commo.cc:143      req.site_id = self_id  (goes on the wire)
     src/deptran/raft/server.cc:2939-42 receiver rejects a candidate not in
                                            current_config_
     src/deptran/raft/server.cc:1565-71 current_config_ holds GLOBAL site ids

   Config::LoadSiteYML (src/deptran/config.cc:336-366) increments site_id
   globally across rows while resetting locale_id per row, so with three
   replicas site_id == 3*partition + locale and the two id spaces coincide
   only for partition 0 — which is exactly why single-group mode (whose one
   worker sits on partition 0) and multi-at-one-partition both work. The same
   mistake also defeats the self-skip at commo.cc:121-124, so a candidate
   RequestVotes its own listener.

   The fix is one argument (`site_id_` in place of `loc_id`). It was NOT made:
   section 12 puts changes to the Raft implementation out of scope, and this
   harness exists to measure before changing. Raised here instead. The
   configuration remains declared in run_sweep.sh so the sweep fails loudly on
   it rather than silently omitting it.

 DEVIATIONS FROM THE WORK ORDER

   * CLAUDE.md mandates running tests through Docker. Docker is not installed
     on this host, so the step-1 dbtest run and every harness run were done
     directly on the host. Recorded in docs/plans/raft-perf-profile.txt.
   * D6 says the CMake target is "added the same way" as raft_lab_standalone.
     raft_lab_standalone uses a bare add_executable inside the RAFT_TEST gate
     with test-only include dirs; raft_bench is registered with add_apps(),
     which is what section 5 of this plan actually points at
     (CMakeLists.txt:1534). add_apps is the correct choice: the driver must
     link the production `mako` library, and it must NOT sit behind RAFT_TEST,
     which would define RAFT_TEST_CORO and invalidate every number (trap T1).
   * The record carries more keys than step 4 suggested, never fewer. The
     additions are cmake_build_type, raft_default_single_group, max_outstanding,
     log_level, proc, role, measured_window_sec, offered_per_sec,
     offered_in_window, applied_in_window, offer_rejected, foreign_applied,
     samples_used, samples_dropped, latency_max_us and latency_cdf_us. Each
     exists because a reader who lacks it can misread the number: log_level in
     particular changes the result, since the apply path logs one INFO line per
     applied entry.
   * A --phase knee was added to run_sweep.sh. It is not part of --phase all;
     it re-derives the offered-rate arrays on a new machine, which the plan
     asks for implicitly ("using the step-1 profile as the midpoint") but gives
     no mechanism for.
