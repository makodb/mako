================================================================================
 THE TWO BRING-UP PATHS ONTO RaftServer
================================================================================
 Written:  2026-09-11, while checking B1 of cpp-to-rust-precheck-raft.txt.
 Why:      B1's proposed fix mentions "the RaftLab harness" and "the worker",
           and the two bring-up paths behind those words are not documented
           anywhere. Sections 1-5 establish what is actually there. Section 6
           then re-tests an objection to B1 that was raised off the back of an
           earlier, partly wrong draft of this file, and concludes that B1 is
           sound for its stated purpose.
 Verified: every claim below was grepped or read in the tree at 2585a128.

================================================================================
 1. THE SHORT VERSION
================================================================================

 There are two independent bring-up paths that both end at a RaftServer, and
 they share exactly one function: RaftFrame::CreateScheduler().

                        PRODUCTION                  LAB / CORRECTNESS
   binary               dbtest, raft_bench          deptran_server
   built when           always                      only if(RAFT_TEST)
   entry               raft_main_helper.cc setup()  s_main.cc RunServers()
   worker class         RaftWorker                  ServerWorker
   worker file          src/deptran/raft/           src/deptran/
                          raft_worker.cc (1154 ln)    server_worker.cc (184 ln)
   processes            3 (localhost, p1, p2)       1
   replicas per proc    1 group, or N in multi      5, one ServerWorker each
   RaftServer per proc  1 or N                      5
   RaftFrame per proc   1 or N                      5
   how load is injected add_log_to_nc()             RaftServer::Start() direct
   test driver          none (it is production)     a Fiber, created inside
                                                      RaftFrame::CreateCommo()

 The lab is not "a path without a worker". It has a worker; it is just a
 different, much smaller class that happens not to be named RaftWorker.
 server_worker.h:15-16 says so:

   // ServerWorker is the small embedded-server harness used by the RAFT_TEST
   // executable. Production Mako creates RaftWorker/PaxosWorker directly.

================================================================================
 2. WHO CREATES WHAT
================================================================================

 The Frame creates less than it looks like. It owns the RaftServer and the
 RaftCommo; the rrr::Server belongs to the worker, in both paths.

   OBJECT            CREATED BY                                  PATH
   RaftFrame         Frame::GetFrame(MODE_RAFT)                  both
                       -> `new RaftFrame()`, frame.cc:13.
                       A FRESH FRAME PER CALL, not a singleton --
                       so the lab has five of them.
   RaftServer        RaftFrame::CreateScheduler(), frame.cc:202  both
                       `svr_ = std::make_unique<RaftServer>()`
                       returned raw via svr_.get() (frame.cc:208, :224)
   RaftCommo         RaftFrame::CreateCommo(), frame.cc:240      both
                       `commo_ = std::make_unique<RaftCommo>(...)`
                       returned raw (frame.cc:321)
   rrr::Server        THE WORKER, in SetupService():             both
                       raft_worker.cc:340   (production)
                       server_worker.cc:72  (lab)
                       -- near-identical lines
   PollThread         the same two SetupService() bodies         both
                       `PollThread::create()`
   RPC services       RaftFrame::CreateRpcServices(), called     both
                       from the worker's SetupService(); ownership
                       moves into rpc_server_ via reg_service_proxy
   heartbeat          RaftWorker::SetupHeartbeat(),              production
     rrr::Server        raft_worker.cc:493, at port + 10000        ONLY
                       (CtrlPortDelta, raft_worker.h:143).
                       ServerWorker::SetupHeartbeat() EXISTS
                       (server_worker.cc:9) but HAS NO CALLER --
                       dead code copied from RaftWorker.

 So the answer to "where is the rrr::Server created": in the worker, not the
 frame, and each path creates its own with the same six lines.

================================================================================
 3. THE SHARED THREE STEPS, SIDE BY SIDE
================================================================================

 Both paths run SetupBase -> SetupService -> SetupCommo. The first two are
 essentially the same code twice; the divergence is all in SetupCommo.

 SetupBase
   production  raft_worker.cc:266   GetFrame, set site_info_, CreateScheduler,
                                    stamp partition_id_/loc_id_/site_id_
   lab         server_worker.cc:32  the same, plus a fail-closed
                                    RegLearnerAction stub so an unexpected
                                    replay aborts startup instead of calling
                                    an empty std::function. RaftLab installs
                                    the real oracle later.

 SetupService
   production  raft_worker.cc:329   PollThread::create, new rrr::Server,
   lab         server_worker.cc:56  admission_ready(false), CreateRpcServices,
                                    reg_service_proxy each, start(bind_addr).
                                    These two bodies are line-for-line
                                    equivalent.

 SetupCommo -- THIS IS WHERE THEY PART
   production  raft_worker.cc:361   CreateCommo, assign rep_sched_->commo_.
                                    That is all. EnsureSetup is dispatched
                                    separately, by the helper, as a OneTimeJob
                                    onto the server PollThread
                                    (raft_main_helper.cc:473-481 single-group,
                                    :542-549 multi-group), followed by
                                    WaitForStartup, SetRpcAdmissionReady,
                                    StartSubmitThread and SetupHeartbeat
                                    (raft_main_helper.cc:498, :575).
   lab         server_worker.cc:110 CreateCommo, assign commo_, then does the
                                    startup itself inline: queues a OneTimeJob
                                    calling rep_sched_->EnsureSetup(), calls
                                    rep_sched_->WaitForStartup(), opens
                                    admission -- and then, for site 0 only,
                                    enters Reactor::run_loop(true, true) and
                                    never returns until the lab test fiber
                                    switches the loop off.

 The last line is the structural difference: in the lab, site 0's SetupCommo
 IS the process's main loop. s_main.cc:41-43 documents the ordering that makes
 this safe -- every site must finish SetupService before any site enters
 SetupCommo, enforced by a mutex/condvar barrier at s_main.cc:53-91, because
 site 0 will not come back.

================================================================================
 4. HOW THE LAB TEST GETS DRIVEN AT ALL
================================================================================

 Nothing external starts the test. It bootstraps from inside the Frame, on the
 way up, and it counts its way there:

   1. s_main.cc:65-91 spawns one std::thread per site; each runs SetupBase,
      SetupService, waits at the barrier, then SetupCommo.
   2. RaftFrame::CreateScheduler() (frame.cc:213-221), when
      IsRaftLabTestConfig(), registers itself: frames_[locale_id] = this and
      n_replicas_++.
   3. RaftFrame::CreateCommo() (frame.cc:243-300), when IsRaftLabTestConfig(),
      verifies all five schedulers exist, increments n_commo_created_, and --
      if locale_id == 0 -- creates the test Fiber.
   4. That fiber yields once, waits for all five communicators, then:
        auto testconfig = new RaftTestConfig(frames_);
        RaftLabTest test(testconfig);
        test.Run();
      (frame.cc:293-296)
   5. Site 0's SetupCommo is meanwhile sitting in run_loop, which is what
      gives that fiber a thread to run on.

 So the static RaftFrame::frames_ map (frame.cc:152) is the harness's whole
 registry, and RaftTestConfig is keyed on it:

   testconf.cc:112  std::map<siteid_t, RaftFrame*> RaftTestConfig::replicas;
   testconf.cc:120  RaftTestConfig::RaftTestConfig(std::map<siteid_t, RaftFrame*>&)

 and every interaction with a replica is `frame->svr_->...`:

   testconf.cc:155-156  RegLearnerAction on frame->svr_
   testconf.cc:182-185  IsDisconnected / GetState
   testconf.cc:307      it->second->svr_->Start(std::move(cmdptr), index, term)

 Counted: 25 `->svr_` in testconf.cc and ZERO in test.cc.

 CAUTION ON THAT COUNT. B1 says "`svr_` 25 times in testconf.cc plus 2 in
 test.cc". The 2 do not exist: both hits are `siteid_t svr_id`, a local at
 test.cc:2503-2504. A bare `grep -o 'svr_'` counts the substring inside
 `svr_id` and reproduces B1's error exactly -- which is how an earlier draft
 of this file "confirmed" it. Use `grep -oE '(->|\.)svr_\b'`.

 test.cc reaches servers only through RaftTestConfig::GetServer
 (testconf.h:195, testconf.cc:690), 25 call sites, so test.cc needs no edits
 at all under B1. Zero occurrences of RaftWorker in test.cc, test.h,
 testconf.cc or testconf.h, and none of them includes raft_worker.h.

================================================================================
 5. WHAT ONLY PRODUCTION HAS -- AND THEREFORE WHAT IS UNTESTED
================================================================================

 The lab reaches RaftServer::Start() directly. Everything RaftWorker adds
 between the application and Start() is exercised by NO correctness test:

   * add_log_to_nc / submit / add_log entry points  (raft_main_helper.cc)
   * IncSubmit / n_submit / n_tot bookkeeping       (raft_worker.cc:778, :774)
   * EnqueueLog and submit_queue_                   (raft_worker.cc:692)
   * SubmitLoop, batch_limit_, the drain loop       (raft_worker.cc:1114)
   * WaitForSubmit                                  (raft_worker.cc:784)
   * CreateRaftLogCommand / TpcCommitCommand wrap   (raft_worker.cc:717)
   * RaftWorker::Next and the whole watermark
     callback registry -- leader/follower maps,
     un_replay_logs_by_partition_, the status word  (raft_worker.cc:914-1085)
   * IsLeader / GetLeaderHint / IsPartition         (raft_worker.cc:600-650)
   * handles_all_partitions_ single-group mode and
     the stub servers that serve the other
     partitions' ports                             (raft_main_helper.cc)
   * the heartbeat rrr::Server at port + 10000      (raft_worker.cc:481)

 Verified: grep for add_log_to_nc, EnqueueLog, SubmitLoop, submit_queue_ and
 WaitForSubmit across test.cc, testconf.cc, server_worker.cc and s_main.cc
 returns nothing.

 The standalone performance harness (src/deptran/raft/raft_bench.cc) is
 currently the only thing in the tree that drives that layer deliberately, and
 it is a performance instrument, not a correctness one.

 6. CONSEQUENCE FOR B1 -- SMALLER THAN IT FIRST LOOKED
================================================================================

 An earlier draft of this file argued that B1's proposed fix does not survive
 section 1. On re-examination that was wrong on two of its three points, and
 the third is a footnote rather than an objection. Recorded here because the
 wrong version was shown to the owner.

 The bar is CONVERSION, not leak-freedom: can the result be expressed as a
 single owner plus borrows, with no deletion through a borrow. B1 clears it.

 WHAT B1 SAYS.  "Change Frame::CreateScheduler() to return
 rusty::Box<TxLogServer> and hold that Box in RaftWorker::rep_sched_; drop
 RaftFrame::svr_ entirely and give the RaftLab harness an accessor that
 reaches the server through the worker."

 POST-FIX OWNERSHIP, both paths. Whoever calls CreateScheduler owns the Box.
 There are exactly two callers and exactly two holders:

   src/deptran/raft/raft_worker.cc:283   rep_sched_   production
   src/deptran/server_worker.cc:40       rep_sched_   lab
   (src/deptran/raft/raft_worker.h:262 GetRaftServer() downcasts;
    src/deptran/server_worker.h:29 is already RaftServer* directly)

 Both become a Box. RaftFrame::svr_ goes away, so raft_worker.cc:564
 `delete rep_sched_` -- the actual defect -- goes away with it. Single owner,
 no delete through a borrow. That is the whole requirement.

 THE THREE EARLIER OBJECTIONS, RE-TESTED.

  (a) "There is no RaftWorker in the lab path to reach through."
      DOES NOT HOLD. B1 says "the worker", not "RaftWorker". In the lab the
      worker is ServerWorker, and it is already the caller of
      CreateScheduler (server_worker.cc:40). Reading B1 as naming a specific
      class rather than a role was a misreading.

  (b) "ServerWorker::rep_sched_ is another raw RaftServer*, so routing through
      it reproduces the borrow."
      DOES NOT HOLD. That describes the PRE-fix state. If CreateScheduler
      returns a Box, ServerWorker::rep_sched_ is the Box. Nothing is
      reproduced.

  (c) "The harness is keyed on RaftFrame*, so this means rekeying
      RaftTestConfig."
      TRUE BUT TRIVIAL, and B1 already prescribes the remedy. The harness uses
      the frame for NOTHING except reaching the server -- every one of the 25
      uses in testconf.cc is `X->svr_`:

        16  second->svr_
         8  frame->svr_
         1  first_frame->svr_

      So no rekeying is needed. Give RaftFrame a non-owning accessor that
      borrows the worker-owned server, and the harness change is mechanical:
      `X->svr_` -> `X->svr()`, 25 sites, all in testconf.cc; test.cc needs
      none, it already goes through RaftTestConfig::GetServer.
      That accessor is exactly the "accessor that reaches the server through
      the worker" B1 asks for. The back-pointer it needs is a borrow, not an
      owner, so Rust models it as & or Weak -- the tree already carries a
      custom Weak<Coroutine> for this shape.

 WHY THE "FRAME KEEPS OWNERSHIP, WORKERS BORROW" ALTERNATIVE IS WORSE.
 The earlier draft proposed it. It is already live in one path and it is the
 reason the leak exists: ServerWorker::ShutDown (server_worker.cc:164-169)
 deliberately skips the delete, with a comment naming RaftFrame::svr_ as the
 owner. Adopting it everywhere means deleting raft_worker.cc:564, which
 `grep -rn "delete rep_sched_"` shows is the ONLY site in the repository that
 destroys a RaftServer (paxos_worker.cc:240 is the Paxos one). That would make
 ~RaftServer (server.cc:2661-2690) unreachable -- and it does real work: it
 nulls async_callback_lifetime_->server under the lifetime mutex and joins
 apply_thread_. Its only Rust spelling is Box::leak -> &'static, which makes
 the leak permanent design rather than converting it. B1's direction is right
 and this alternative should not be pursued.

 THREE THINGS B1 DOES NOT MENTION.
 (1) CreateScheduler is currently idempotent-ish: a second call logs an error
     and returns the EXISTING svr_.get() (frame.cc:198-209). A function
     returning Box cannot do that. The branch is unreachable -- both SetupBase
     implementations call Frame::GetFrame() first and GetFrame returns
     `new RaftFrame()` every time (frame.cc:13), so every frame is fresh and
     sees exactly one call. Deleting it is what MAKES the Box return sound,
     and it is a benefit B1 never claims.

 (2) The two rep_sched_ slots are not the same shape, though B1 says
     server_worker.cc:40 "performs the same dynamic_cast".
       raft_worker.h:121   TxLogServer* rep_sched_    -- an UPCAST slot, which
                           rusty::Box's converting ctor handles
       server_worker.h:29  RaftServer*  rep_sched_    -- a DOWNCAST slot
     dynamic_cast on a Box prvalue is ill-formed, and rep_sched_ occurs 15
     times in server_worker.cc, not the 1 B1 budgets. Mechanical either way:
     retype the lab field to Option<Box<TxLogServer>> and downcast the borrow,
     or add a concrete RaftFrame::CreateRaftScheduler() -> Box<RaftServer>
     (available because ServerWorker::rep_frame_ is already RaftFrame*,
     server_worker.h:27).

 (3) Drop order. raft_worker.h declares rep_sched_ at :121 and rpc_server_ at
     :127. Rust drops fields in declaration order, so a naive port drops the
     SERVER FIRST -- into live RaftServiceImpl handlers that hold a bare
     RaftServer* (service.h:31) with no lifetime lease. What makes today's C++
     safe is the explicit ShutDown sequence: StopSubmitThread ->
     set_admission_ready(false) + drain (raft_worker.cc:526-533) ->
     PrepareForShutdown (:542) -> delete rpc_server_ (:552) -> delete
     rep_sched_ (:564). The Box drop must keep that position, or the two
     declarations must be swapped. A defect entry whose claim is "single clear
     owner" should say so.

 WHAT STILL STANDS FROM THIS FILE. Not an objection to B1, but B1 should
 record it: a RaftWorker conversion cannot be validated by the correctness
 suite, because section 5's list -- the submit queue, batching, Next() and the
 watermark callback registry, IsLeader, the stub servers, the heartbeat server
 -- is exactly what such a conversion changes, and none of it is exercised by
 test.cc or testconf.cc. B1's blast-radius paragraph counts the edit sites
 accurately; it does not say that 23 of them are untested.
