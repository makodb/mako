 0.5 METHOD

 Every item was audited once and then checked by two independent adversarial
 verifiers whose brief was to refute it. Their corrections are folded in
 rather than appended: where a claim was refuted it has been removed or is
 stated in its corrected form, and where the correction changes the reading
 the paragraph says so. Nine findings were withdrawn or materially
 rewritten as a result, the largest being:

   - The "unbounded leak" of the malloc'd un-replay buffer. It is freed, at
     src/mako/mako.hh:308 and :313 (OUT OF SCOPE, verified). What survives is
     a raw malloc/free pair split across a module boundary. See LIF-07.
   - The claim that janus::leader_callback_ is never invoked, so Raft
     silently drops leadership registrations. It is read at
     raft_main_helper.cc:1197 and :1287 and invoked at :1200 and :1290
     (production, verified). The proposed deletion would have removed
     working code. See ERR-06.
   - The claim of a window in which IsLeader() lies about leadership. Not
     demonstrated; the fiber that sets looping_ runs synchronously from
     SetupInternal. See LIF-02.
   - The "raw 25 ms usleep" at server.cc:3443. It is inside a /* */ comment
     opened at server.cc:3442 (verified). There is no usleep in production
     Raft. See LIB-05.
   - The concurrent-map-mutation mechanism behind OWN-03. The keys are never
     absent, so no rebalance occurs; what survives is a borrow held across a
     yield point. See OWN-03.

 A THIRD adversarial pass, run against this text rather than against the
 code, corrected seven substantive things and five counts. The substantive

   - The production OWN-02 read at raft_main_helper.cc:959 is reached only

 0.6 ONE EMPIRICAL CORRECTION TO docs/stage2_raft.txt

 Section 6 of that record says raft carriers get no ODR post-pass, and
 concludes that header-resident types cannot carry methods. Probing the
 pinned emitter shows a `pub const fn` inside an `impl` emits `constexpr`,
 which is implicitly inline, so header-resident types CAN carry const
 methods today. Non-const out-of-line methods still cannot. This matters in
 two places below: it does not rescue destructors (LIF-05), and it does not
 rescue a non-const allocating factory such as `RaftServer::new_`
 (LIF-01).

================================================================================
 2. THE ROOT DEFECTS
================================================================================

 The 11 BLOCKER verdicts are not 11 independent problems. They reduce to
 six root defects, each of which carries several checklist ids because the
 checklist looks at the same construct from several angles. A seventh defect,
 B4, is given here with them because it is one defect behind three ids
 (OWN-04, CON-06, half of CON-02) even though those are graded MAJOR; the
 grading note under B4 says why. They are given as defects rather than as
 rows, ordered by how much they block: B1 and B2 must be settled before
 almost anything else can be ported, B6 and B7 are blocking but local.

--------------------------------------------------------------------------------
 B1. RaftServer IS DOUBLY OWNED, AND THE LEAK IS WHAT MAKES IT SAFE
     Carries LIF-07, OWN-01, OWN-05.  production.
--------------------------------------------------------------------------------

 WHAT IT IS. RaftServer is allocated into a unique_ptr owned by RaftFrame and
 then deleted through a raw pointer held by RaftWorker, while the unique_ptr
 still holds it. This is not a double free only because nothing in the
 repository ever deletes a Frame.

   frame.cc:202       `{ svr_ = std::make_unique<RaftServer>(); }`
   frame.h:46         `std::unique_ptr<RaftServer> svr_;  // @unsafe -
                       unique_ptr kept for test file compatibility`
   frame.cc:208, :224 `return svr_.get();`         -- the raw pointer escapes
   raft_worker.cc:283 `rep_sched_ = rep_frame_->CreateScheduler();`
   raft_worker.h:121  `TxLogServer* rep_sched_ = nullptr;  // Points to
                       RaftServer`
   raft_worker.cc:564 `delete rep_sched_;`         -- deletes what svr_ owns
   src/deptran/frame.cc:13 (PARENT) `case MODE_RAFT: return new RaftFrame();`

 `grep -rn 'delete.*[Ff]rame' src/deptran src/mako --include=*.cc` returns
 nothing, and `RaftFrame::~RaftFrame()` (frame.cc:141-142) has an empty body.
 So `svr_` dangles from raft_worker.cc:564 to process exit and its destructor
 never runs. The communicator has the same shape and is resolved purely by
 the leak: frame.cc:240 `commo_ = std::make_unique<RaftCommo>(...)`, handed
 out raw at frame.cc:321, aliased by `raft_worker.h:122 Communicator*
 rep_commo_`, never deleted -- so `Communicator::~Communicator()`
 (communicator.h:62) never runs and every peer connection stays open.

 WHY IT BLOCKS. Rust cannot express deletion through a borrowed pointer.
 There is no `Box` to hand `rep_sched_`, and no `&mut` that may be dropped.
 Any Rust port must first decide who owns a RaftServer, and today the answer
 is "two places, and the second one wins because the first one is leaked".
 It also blocks B3: a fallible factory has nowhere to return to while the
 frame both owns the object and publishes a raw alias to it.

 PROPOSED FIX. Change `Frame::CreateScheduler()` to return
 `rusty::Box<TxLogServer>` and hold that Box in `RaftWorker::rep_sched_`;
 drop `RaftFrame::svr_` entirely and give the RaftLab harness an accessor
 that reaches the server through the worker. The upcast works today:
 `rusty::Box`'s converting move constructor
 (third-party/rusty-cpp/include/rusty/box.hpp:259-263) is gated on
 `std::is_convertible<U*,T*>`, and `virtual ~TxLogServer()` (scheduler.h:29,
 defined scheduler.cc:5) makes delete-through-base well defined.

 BLAST RADIUS, measured. The pure virtual is at src/deptran/frame.h:26 and is
 shared with Paxos, so both implementations change: src/deptran/raft/frame.cc
 and src/deptran/paxos/frame.cc (OUT OF SCOPE but unavoidable), plus
 src/deptran/server_worker.cc:40, which performs the same
 `dynamic_cast<RaftServer*>(rep_frame_->CreateScheduler())`. Inside scope:
 `rep_sched_` occurs 23 times in raft_worker.cc; `frame->svr_` occurs 9 times
 in testconf.cc (all TEST-ONLY), and `svr_` 25 times in testconf.cc plus 2 in
 test.cc. Doing the same for `commo_`/`rep_commo_` costs a further ~6 sites.
 Call it 35 in-scope edits plus 3 out-of-scope files. This cannot be done
 raft-only.

--------------------------------------------------------------------------------
 B2. TxLogServer::mtx_ IS A PUBLIC RECURSIVE MUTEX THAT OWNS NO DATA
     Carries CON-01, CON-05, OWN-02, and the TxLogServer half of TYP-01.
     PARENT plus production.
--------------------------------------------------------------------------------

 WHAT IT IS. One line in a 36-line base class is the root of the whole
 concurrency category:

   scheduler.h:26   `std::recursive_mutex mtx_{};`   -- in the public section

 Three properties, each independently fatal to a `Mutex<T>` translation.

 (a) It owns nothing. It guards roughly 25 RaftServer members that are
     declared beside it rather than inside it. Thirteen of them are public:
     the only `public:` in `class RaftServer` is server.h:1545 (verified by
     scanning 1170-1996: `private:` at 1171, `public:` at 1545, nothing
     else), and it exposes server.h:1584-1599 -- `min_active_slot_`,
     `max_executed_slot_`, `max_committed_slot_`, `logs_`, `n_vote_`,
     `n_prepare_`, `n_accept_`, `n_commit_`, `lastLogIndex`, `currentTerm`,
     `commitIndex`, `executeIndex`, `raft_logs_` -- plus six more inherited
     from scheduler.h:21-26. It is locked at 37 `lock_guard` sites inside
     the class (30 in server.cc, 7 in server.h; 2 further `unique_lock`s at
     server.cc:2807 and :3165) and reached into from outside at 25 more
     (server.cc:2108 production, and 24 in test.cc, e.g. test.cc:123
     `std::lock_guard<std::recursive_mutex> lock(server->mtx_);`).

 (b) It is recursive, and the recursion is load-bearing, not incidental.
     Twenty-four lexically nested re-acquisitions exist in production
     (server.cc:869, 1271, 1758, 1781, 1968, 2393, 2435, 2616, 2772, 2833,
     2875, 2884, 2891, 2897, 3113, 3122, 3271, 3281, 3294, 3572, 3583, 3756;
     server.h:1505, 1662), reaching depth 4:

       OnRequestVote (server.cc:2928 locks)
         -> doVote (server.h:1386, no lock)
           -> stepDown (server.cc:3795, no lock)
             -> resetTimer (server.h:1501 locks, depth 2)
               -> GetElectionTimeout (server.cc:1260 locks, depth 3)
                 -> AmIPreferredLeader (server.h:1363 locks, depth 4)

     The design is deliberate and documented as such: server.h:1360-1361
     says "The mutex is recursive because consensus paths commonly call this
     helper while already holding mtx_".

 (c) Protected data escapes the lock in four distinct shapes: ten
     reference-returning `LabAccess` accessors (server.h:1565-1577, e.g.
     `static bool& is_leader(RaftServer& s) { return s.is_leader_; }`,
     TEST-ONLY but in a production header); a `MemorySnapshotWriter` holding
     four raw pointers into its manager including the mutex
     (memory_snapshot_manager.hpp:126-129, handed over at :179);
     `RpcPeer::WithClient` returning a mutable client pointer through a
     const_cast (communicator.h:38, PARENT); and a `std::map` iterator into
     `next_index_` formed outside the lock and held across RPC sends
     (server.cc:2036, see OWN-03).

 WHY IT BLOCKS. Rust's std has no reentrant mutex, and
 `parking_lot::ReentrantMutex` hands out `&T`, never `&mut T`. Twenty-four
 nested re-acquisitions of a mutex guarding mutable state therefore have no
 Rust spelling at all. This is the precondition of CON-01: the
 `Mutex<RaftState>` enclosure cannot be built while the mutex is reentrant.

 PROPOSED FIX, in two ordered steps.

 (1) Remove the reentrancy. The pattern is already proven in this file by
     four existing `*Locked` methods (server.h:1221, 1229, 1242, 1328): split
     each self-locking helper into a public `X()` that locks and a private
     `XLocked()` that does not, then point the 24 nested sites at the
     `Locked` form. The seven helpers actually reached from a locked region
     are IsLeader, setIsLeader, resetTimer, AmIPreferredLeader,
     GetElectionTimeout, SetLocalAppend and PublishAppliedIndex.
     (`GetPreferredLeader`, server.h:1962, is often listed with them but has
     zero callers repo-wide -- delete it instead.) Blast radius: 7 method
     splits, 24 nested sites, and roughly 30 unnested callers that keep the
     locking form -- about 60 local edits, each individually verifiable.
     One precondition is unresolved: mtx_ is currently held from
     server.cc:2058 across the send at :2095 while the reply lambda re-locks
     `server->mtx_` at :2108, so a non-recursive mutex self-deadlocks if that
     callback can ever run inline. See open question Q3.

 (2) Add `rusty::Mutex<RaftState>` to RaftServer holding the ~25 guarded
     fields, and make the public members private. Do NOT delete
     `TxLogServer::mtx_`: `class PaxosServer : public TxLogServer`
     (src/deptran/paxos/server.h:25, OUT OF SCOPE) uses it at 6 sites
     including a manual `ps->mtx_.lock()` / `.unlock()` pair at
     paxos/server.cc:34/60. Blast radius: 37 production lock sites, 24
     external test locks, 47 direct external field accesses in test.cc, 45
     `LabAccess::` uses (44 in test.cc, 1 in testconf.cc) and 1 in
     raft_main_helper.cc -- roughly 154 sites. This is the largest single
     change in the audit and should be staged on its own.

--------------------------------------------------------------------------------
 B3. RaftServer TAKES SIX ORDERED PHASES TO BECOME USABLE; RaftWorker NINE
     Carries LIF-01, LIF-02.  production.
--------------------------------------------------------------------------------

 WHAT IT IS. A constructed RaftServer is not a RaftServer. Six phases are
 mandatory and ordered, and every ordering constraint is enforced by an abort
 or by silence rather than by a type:

   P1  ctor                     server.cc:1169
   P2  identity injected by writing three public inherited fields
       raft_worker.cc:288-290   `rep_sched_->loc_id_ = site_info_->locale_id;
                                 rep_sched_->site_id_ = site_info_->id;
                                 rep_sched_->partition_id_ = ...`
       against scheduler.h:21-25 (PARENT)
   P3  learner bound            raft_worker.cc:444 `RegLearnerAction(...)`
   P4  communicator injected    raft_worker.cc:374 `rep_sched_->commo_ =
                                 rep_commo_;`
   P5  EnsureSetup()            server.cc:3783 -> Setup() 1622 ->
                                 SetupInternal() 1490
   P6  WaitForStartup()         server.cc:1647
   and a mandatory teardown phase PrepareForShutdown() (server.cc:1219)
   before ~RaftServer (server.cc:2661).

 Skipping P4 aborts rather than failing: `commo()` (server.h:1547-1551) does
 `verify(communicator != nullptr)`, and there are 6 `commo()` call sites in
 server.cc (1519, 1520, 1656, 2095, 2327, 2803). P5's idempotence rests on an
 unsynchronised bool (`heartbeat_setup_`, server.h:1305, checked and set at
 server.cc:3783-3789), and `StartApplyThread` (server.cc:1344-1346) has no
 guard at all, so a lost race assigns over a joinable `std::thread` and calls
 std::terminate.

 The constructor cannot report failure, escapes `this` twice before the
 object is complete, and mutates a process-global registry:

   server.cc:1172-1173  `install_snapshot_callback_gate_(
                          rusty::Arc<InstallSnapshotCallbackGate>::make(this))`
   server.cc:1175       `async_callback_lifetime_->server = this;`
   server.cc:1178       `EnsureLegacyRaftLogPayloadRegistered();`
                        -> `rrr::SerializableRegistry::reg<LegacyVecPieceData>`
                           (src/deptran/legacy_raft_log_payload.cc:219-225,
                           OUT OF SCOPE, traced)

 All fallible work is deferred into `bool SetupInternal()` (server.cc:1490-
 1618), whose four failure exits (return false at 1510, 1529, 1545, 1558)
 each write two atomics and leave the reason only in a log line; and into
 `bool InitializeSnapshotManager()` (server.cc:676), which collapses eight
 distinct failure reasons into one `false` through a shared `fail_recovery`
 lambda at server.cc:734 (returns at 752, 767, 771, 776, 781, 785, 823, 836).
 Not one constructor or factory in the entire 32-file scope returns
 `expected`/`Result`; the only `rusty::Result` surface is the four GENERATED
 RPC signatures at service.h:40-43, forced by rcc_rpc.h:698-704.

 RaftWorker layers nine more setup methods on a defaulted constructor
 (raft_worker.cc:250 `RaftWorker::RaftWorker() = default;`): raft_worker.h:153
 SetupBase, :155 SetupService, :157 SetupCommo, :160 PrepareForStartup, :163
 WaitForStartup, :165 SetRpcAdmissionReady, :167 FinishStartup, :169
 SetupHeartbeat, :177 StartSubmitThread -- plus two public-field writes. Two
 of those guards are aborts (raft_worker.cc:363-364), but SetupService before
 SetupBase silently opens a listening socket with no Raft service registered,
 because raft_worker.cc:344 is `if (rep_frame_ != nullptr) {` while
 raft_worker.cc:354 `rpc_server_->start(...)` runs regardless. There are also
 two competing startup protocols for the same object: `FinishStartup`
 (raft_worker.cc:472-478) is dead repo-wide, and the production entry point
 instead uses a split barrier at raft_main_helper.cc:557-568.

 WHY IT BLOCKS. Rust has no partially-initialised object. `Arc::new_cyclic`
 or an explicit post-construction bind is required for the `this`-escape, a
 `OnceLock` for the registry mutation, and the six phases must collapse into
 a factory plus a typestate before any of the affected types can be written
 in safe Rust.

 PROPOSED FIX.

   static rusty::Result<rusty::Box<RaftServer>, StartupError>
   RaftServer::new_(RaftServerConfig)

 where `RaftServerConfig` carries loc_id, site_id, partition_id, the
 RaftCommo handle, the learner action, the optional SnapshotManager and the
 three env-derived knobs SetupInternal reads today -- folding P2, P3 and P4
 into construction and deleting the `commo()` verify. Then split the runtime
 start into a typestate: `start(self) -> Result<Box<RunningRaftServer>, E>`,
 with IsLeader/Start/GetLeaderHint/RegisterLeaderChangeCallback hanging off
 the running type only. Move `EnsureLegacyRaftLogPayloadRegistered()` into a
 module-level `OnceLock`, and replace the `this`-escape with an explicit
 `bind_gates(&Arc<Self>)`.

 One feasibility caveat the audit could not settle: RaftServer is declared in
 a header (server.h:1170), `new_` is non-const and allocating, and raft
 carriers get no ODR post-pass -- so the `pub const fn` -> `constexpr` escape
 hatch does not apply. Whether `RaftServer::new_` is expressible in the DSL
 at all is open question Q1.

 BLAST RADIUS. About 15 production call sites (raft_worker.cc:283, 288-290,
 374, 444; raft_main_helper.cc:457, 466, 468, 476, 481, 485, 490, 514-516,
 527-537, 545, 549, 557-568), plus the 9 RaftWorker setup declarations at
 raft_worker.h:153-177, plus the TEST-ONLY harness surface (27 `svr_` uses
 across testconf.cc and test.cc).

 B4. STORED CALLBACKS AND UNJOINED FIBERS HOLD RAW `this`
     Carries OWN-04, CON-06, and the fiber half of CON-02.  production.
     MAJOR, not blocking -- see the grading correction below.
--------------------------------------------------------------------------------

 WHAT IT IS. Nine long-lived captures of a raw `this` or a bare pointer cross
 a thread or callback boundary, and exactly one of them has any lifetime
 guard. Three shapes matter.

 (a) Three fibers spawned with no join handle:
     server.cc:1602 and :1609 (production arm, `#ifndef RAFT_TEST_CORO`;
     the `#ifdef` arm at 1583/1590 is the TEST_CORO twin) and server.cc:3024
     `Fiber::create_run([this]() {`. `Fiber::create_run` returns nothing to
     join on, so the only teardown mechanism is the atomic completion barrier
     polled at server.cc:1233-1239.

 (b) Two raw back-pointers stored inside RaftServer by RaftWorker, with no
     unregister path:
     raft_worker.cc:294 `raft_server->RegisterLeaderChangeCallback(
                          [this](bool leader) { ... })`
       -> stored in `leader_change_cb_` (server.h:1331), fired at
          server.cc:1796 and :1799
     raft_worker.cc:381 `auto learner = std::bind(&RaftWorker::Next, this,
                          ...)` installed at :444 into
          `TxLogServer::app_next_` (scheduler.h:23, PARENT), invoked at
          server.cc:1402 and :1838
     The cycle is raft_workers_g -> shared_ptr<RaftWorker> -> rep_frame_ ->
     unique_ptr<RaftServer> -> std::function -> RaftWorker*.

 (c) Two competing async-lifetime mechanisms, of which the newer is dead
     code. `InstallSnapshotCallbackGate` (server.cc:332-390) and its RAII
     `InstallSnapshotCallbackLease` (server.cc:395-419) implement a packed
     borrow count -- and `InstallSnapshotCallbackLease` is constructed
     nowhere in the repository; `TryAcquire()` is called only from its own
     constructor at server.cc:399. So `ActiveCallbacks()` is structurally
     always zero, and both the drain loop at server.cc:1237 and the
     assertion at server.cc:2673 `verify(install_snapshot_callback_gate_
     ->ActiveCallbacks() == 0)` are vacuous. The one real InstallSnapshot
     callback instead resurrects a raw `RaftServer*` out of a shared_ptr
     (server.cc:2101-2108) and mutates term and leadership state
     (server.cc:2121, 2122, 2129, 2132). That mechanism is itself sound --
     ~RaftServer nulls the pointer under the same mutex at server.cc:2676-
     2677 -- but nothing waits for it: PrepareForShutdown never nulls it, so
     between PrepareForShutdown and ~RaftServer a reply callback can still
     take mtx_ and rewrite the term of a server that believes it is down.
     The comment at server.h:1314-1317 claims these callbacks "capture only
     this independently owned gate, never a RaftServer raw pointer", which
     the only callback in the tree contradicts.

 WHY IT MATTERS, AND A GRADING CORRECTION. The first pass graded OWN-04 and
 CON-06 BLOCKER on the absence of a join handle. That is wrong against this
 report's own rubric ("no safe-Rust spelling of the construct"): safe Rust
 spells both shapes without a join -- a detached task owning an
 `Arc<RaftServer>` for (a), since a dropped `JoinHandle` detaches, and `Weak`
 or a channel for (b). That is the same fix and the same obstacle CON-02
 grades MAJOR for the two `std::thread` captures: the pointee is not
 Arc-owned, which is B1's defect, so B4 sequences after B1 rather than ahead
 of it. Both ids are therefore MAJOR. What remains genuinely unfixable inside
 this scope is narrower than the first pass claimed: `Fiber::create_run`
 offers no handle at all, so the C++ cannot be given a structured join before
 conversion, and adding one is an rrr-side change.

 PROPOSED FIX. Delete the dead gate, keep the working mechanism, and convert
 it: remove server.cc:332-418, server.h:52 and :1317, and the four vacuous
 sites (server.cc:1230, 1237, 2667, 2673); then port
 `AsyncCallbackLifetime` to `Weak<Mutex<RaftState>>`, which is what it
 hand-rolls. Do NOT adopt the gate instead: `TryAcquire` returns a bare
 pointer with no mutual exclusion against the destructor body, and
 ~RaftServer *verifies* rather than drains, so wiring real leases would turn
 a currently-vacuous assertion into a live abort whenever a snapshot reply is
 in flight at destruction without a prior drain (the drain lives in
 PrepareForShutdown at server.cc:1233-1245, and the destructor is documented
 at server.cc:2661-2663 as reachable without it). Blast radius: 1 callback
 body, 1 struct plus 1 field (server.h:1174-1180), the gate's 90 lines, and
 4 lifecycle sites.

 For (b) the Rust shape is a channel: RaftServer sends `LeaderChanged(bool)`
 and `Apply(slot, cmd)`, the worker owns the receiver. Blast radius: 2
 registration sites and 4 invocation sites (server.cc:1402, 1838 for
 app_next_; 1796, 1799 for leader_change_cb_) plus the worker loop -- but it
 depends on the apply path becoming asynchronous, and `Next()` currently
 returns a status code synchronously, so this needs a behavioural decision
 first. For (a) there is no fix inside this scope: `Fiber::create_run` has no
 join handle and adding one is an rrr-side change (OUT OF SCOPE).

 B5. DESTRUCTORS THROW, AND `pub trait` GATES SEVEN MORE
     Carries LIF-05.  production, plus a GENERATED constraint.
--------------------------------------------------------------------------------

 WHAT IT IS. Two independent problems in one place.

 (a) `~RaftServer` (server.cc:2661-2690) contains three `verify()` calls at
     server.cc:2667-2673, and `verify` throws in this build. The chain is
     verify (src/rrr/base/debugging.rs:143-152) -> verify_failed (:125-136)
     -> `rusty::panic::do_panic` -> `throw std::runtime_error`
     (third-party/rusty-cpp/include/rusty/panic_handler.hpp:37-46), because
     `RUSTY_PANIC_ABORT` is defined in no CMakeLists.txt, Makefile or cmake/
     file in this repository. So a mis-sequenced teardown terminates with
     "terminate called after throwing" out of an implicitly-noexcept
     destructor rather than asserting. The same destructor also joins a
     thread (server.cc:2685, can throw std::system_error) and takes a mutex
     (:2676). Exactly one destructor in the whole scope is declared noexcept,
     and it is TEST-ONLY: test.cc:33 `~RaftTestScopeExit() noexcept`.
     Two more instances of the same class: `~InMemoryLogStorage`
     (memory_log_storage.hpp:115-117) calls close(), which does
     `logs_.lock().unwrap()`, and unwrap on Err throws
     (rusty/result.hpp:173/175); and `~RocksDBLogStorage`
     (rocksdb_log_storage.hpp:247) discards the bool from a fallible
     `close()`. Both are in Storage-group files that no Raft translation unit
     includes on this branch, so they are latent.

 (b) Per docs/stage2_raft.txt section 7, a `pub trait` is not a drop-in for a
     pure-virtual class: the emitted destructor becomes `noexcept(false)` and
     copy and move are deleted. Nine defaulted virtual destructors in scope
     are gated by that -- the seven raft interfaces (log_storage.hpp:250,
     dispatcher.hpp:48, transport.hpp:57, snapshot_manager.hpp:81, :121,
     :166, server.h:62) plus the two PARENT ones, `virtual ~Frame() = default`
     (frame.h:24) and `virtual ~TxLogServer()` (scheduler.h:29, defined
     scheduler.cc:5). These are the *compliant* interfaces; the constraint is
     that even they cannot move yet.

 Separately, teardown order is external and unenforced. `~RaftWorker`
 (raft_worker.cc:253-263) does only StopSubmitThread plus two poll
 shutdowns, while the real teardown is `ShutDown()` (raft_worker.cc:511-584),
 whose internal order is load-bearing and documented as such at
 raft_worker.cc:517-524 and :536-543. Process teardown is a four-step
 externally sequenced protocol at raft_main_helper.cc:966-993. And the
 failure path bypasses all of it: `finish_launch(false)`
 (raft_main_helper.cc:146-150) only sets a state flag, so the early returns
 at :487-488 and :561-562 leave every global populated and RaftWorkers reach
 static destruction with ShutDown() never called.

 WHY IT BLOCKS. A throwing destructor has no Rust analogue -- `Drop` cannot
 fail -- and (b) changes the exception specification on every derived
 destructor, so the interfaces cannot be expressed as traits without an
 emitter change. The `pub const fn` -> `constexpr` correction does not help:
 destructors are not const fns.

 PROPOSED FIX. For (a), the highest-value action is a decision rather than an
 edit: define `-DRUSTY_PANIC_ABORT` so `verify()` terminates. That is one
 build-flag line, but it changes the meaning of every catch clause in scope
 at once and is not safely raft-scoped -- see ERR-01 for why, and Q2. Failing
 that, replace the three verifies in ~RaftServer with an explicit
 `std::abort()` after a Log_fatal (one file, zero call sites). For teardown,
 move the body of `ShutDown()` into `~RaftWorker` and make the public
 `ShutDown()` an idempotent wrapper, so a RaftWorker cannot be destroyed
 half-torn-down; blast radius is the two happy-path loops
 (raft_main_helper.cc:966-968, 976-978) plus the failure path above. For (b)
 the audit has no fix: it looks like an emitter change, and is stated as an
 open question rather than a plan.

 The weakest axis for a Rust port after object lifecycle, and nothing in this
 category is CONVERTED: a mechanical scan of every `#if RUSTYCPP_RUST` body

 WHAT THEY DO NOT COVER, stated plainly because it is what section 2 is about

 - No mutex, atomic, thread, channel or callback appears inside ANY of the 26
   blocks. A mechanical scan of every block body confirms it. Every finding in
   the concurrency category is therefore unconverted hand-written C++.
 - No type with a destructor, no factory, no owning pointer and no container
   member is inside a block. So none of the seven root defects is inside
   converted code, and none of them is caused by the DSL.
 - Two blocks sit in files that no Raft translation unit reaches:
   `raft_rocksdb_log.scalar_decisions` and `raft_memory_log.scalar_decisions`

 - One block is TEST-ONLY (`raft_testconf.index_math`, testconf.cc:58) and
   one is in a TEST-ONLY file (`raft_channel_transport.scalar_decisions`).

 - The term-zero sentinel protocol is now Rust: server.h:246 `pub const fn

================================================================================
 6. OPEN QUESTIONS FOR THE OWNER
================================================================================

 These are the things the audit could not settle. They are ordered by how
 much they change the plan in section 5.

 Q1. Is `RaftServer::new_` expressible in the DSL at all?
     RaftServer is declared in a header (server.h:1170), a factory is
     non-const and allocating, and raft carriers get no ODR post-pass. The
     `pub const fn` -> `constexpr` correction in section 0.6 rescues const
     header-resident methods but not this. If the answer is no, item 16 needs
     a different shape (a free function in a .cc carrier, or a header type
     whose factory stays C++), and B3's fix as written does not land.

 Q2. Is unwinding the intended panic strategy, or an oversight?
     `RUSTY_PANIC_ABORT` is defined in no CMakeLists.txt, Makefile or cmake/
     file, so `verify()` throws. docs/migration/rustycpp/raft-rust-migration.md
     states no choice. If abort is intended, one flag inverts the semantics
     of all 22 catch clauses and 76 verify sites at once -- but it is
     repo-wide by construction, it breaks the deliberate guard test at
     src/rrr/tests/rpc_frame_codec_test.cc:490-530 (whose comment says the
     throw semantics are "a property ~1,940 call sites now depend on"), and it
     converts rrr's connection-callback panic-swallowing into process death.
     If unwinding is intended, the 76 verify sites need reclassifying,
     because they are documented as invariant checks and behave as
     recoverable errors.

 Q3. Can the InstallSnapshot reply callback run on the thread that launched
     it, and can it run inline?
     mtx_ is held from server.cc:2058 across the send at :2095, and the reply
     lambda re-locks `server->mtx_` at :2108. If that callback can ever run
     inline, item 14's non-recursive mutex self-deadlocks. The audit
     established that RaftCommo shares the worker poll thread
     (raft_worker.cc:334 -> :340, cloned at :369) so delivery is same-thread
     and cooperative -- which is also why OWN-03's traversal is not a data
     race -- but did not establish whether `Future` completion can be
     synchronous with `SendInstallSnapshot`. This must be settled before 14.

 Q4. Is `RaftFrame`'s leak deliberate?
     Nothing in the tree deletes a `Frame`, and that is the only reason
     `delete rep_sched_` at raft_worker.cc:564 is not a double free against
     `RaftFrame::svr_`. If anyone adds `delete rep_frame_` to `~RaftWorker`
     it becomes an immediate double free. The audit found no comment either
     way.

 Q5. Was `InstallSnapshotCallbackGate` built ahead of its adoption, or did a
     callback that used to take the lease get rewritten onto
     `AsyncCallbackLifetime`?
     The answer does not change item 17's action -- the audit recommends
     deleting the gate either way, because adopting it would convert a
     vacuous assertion into a live abort -- but it changes whether the 90
     lines are speculative work or a regression, and therefore whether the
     comment at server.h:1314-1317 should be corrected or removed. Git
     history for server.cc:332-420 versus server.h:1172-1180 would settle it.

 Q6. Should the three unreachable accessors survive? (Section 5 item 1 no
     longer deletes them, precisely because this is open.)
     docs/raft-memory-only.txt section 4.6 says "current_config_ survives as
     the static membership set that GetQuorumSize and HeartbeatLoop iterate",
     but `GetQuorumSize`, `GetCurrentConfig` and `GetCurrentConfigSnapshot`
     all have zero callers repo-wide, and HeartbeatLoop computes the majority
     inline from a per-round copy (server.cc:1994-2007). Delete them before
     conversion, or is a caller expected to return with ReadIndex (open item
     O3 in that record)?

 Q7. Is `raft_server_follower_next_index(UINT64_MAX) == 0` protocol-correct?
     It is pinned twice by static_assert (server.h:1096-1114) and spelled
     with `wrapping_sub`, so it is legitimate Rust and not a translation
     problem. Whether an all-ones next_index wrapping to 0 is intended Raft
     behaviour or a latent bug is a question the type system cannot answer,
     and it should be confirmed before the assert is carried into Rust.

 Q8. Is the snapshot wire format meant to be portable across hosts?
     snapshot_format.hpp:582 and :635 blit `SnapshotHeader` whole, exposing
     native endianness and struct padding, while application_log.cc:16-29
     encodes explicit little-endian. Related and independent of the answer:
     the header CRC length of 44 (snapshot_format.hpp:569, 657, 759) is
     WRONG -- `header_crc` sits at offset 46, so the top two bytes of
     `timestamp_ms` are unprotected. Writer and reader share the mistake so
     nothing fails, but fixing the codec changes the CRC value, so the port
     cannot be byte-identical here. Confirm whether anything persists or
     transmits these bytes across versions before choosing.

 Q9. Can bin/rpcgen emit a bytes type for `string data` (rcc_rpc.rpc:60)?
     If not, `RpcInstallSnapshotRequest::data` stays `std::string` and the
     byte/text separation must terminate at the generated boundary with one
     isolated `@unsafe` conversion. CLAUDE.md permits exactly that for rrr
     wire types, but it should be a recorded decision rather than an accident
     of the generator. The same question governs whether ERR-02's third
     InstallSnapshot reply state is reachable at all, since the reply carries
     exactly one out-field.

 Q10. Is `rusty::Slice` usable in a virtual signature under the pinned
     emitter?
     Fifteen files include `<rusty/slice.hpp>` and instantiate no
     `rusty::Slice` at all (only `rusty::len` and `rusty::as_bytes`, 5 uses,
     all in raft_main_helper.cc). LIB-02's fix assumes the slice type can
     appear in `SnapshotWriter::Write`. If it was never adopted for a reason,
     that fix needs a different byte type.

 Q11. Does anything other than `ServiceBoxShim<RaftServiceImpl>`

 Q12. Does `marshallable_cast<T>(const Command&)` return an owning handle or

 Q13. How deep is RaftServer's coupling to `rrr::PollThread` and

 Q14. Is `slow()` ignoring its `svr` argument (testconf.cc:683-686) a
