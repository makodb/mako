================================================================================
 1. WHY THIS BRANCH EXISTS
================================================================================

 The Rust conversion (docs/stage2_raft.txt) stalled on two gates, and its
 data-structure classification put the whole memory/durable two-tier design
 in Class A, "on the boundary, do not convert without review". The owner's
 decision is to convert the in-memory consensus first and bring disk
 persistence back afterwards. This branch produces that smaller codebase:
 the Raft that Mako production actually runs today.

 That last point is the load-bearing fact. Production never configures a
 LogStorage, a SnapshotManager or a ReplicatedDB: those are opt-in through
 environment variables read in RaftServer::SetupInternal (MAKO_RAFT_PERSISTENCE,
 MAKO_RAFT_SNAPSHOTS, MAKO_REPLICATED_DB), and no example script, CI script
 or config sets them. Only the RaftLab harness (testconf.cc) and the
 persistence test arms turn them on. So removing the disk side removes code
 that production does not execute, and the memory path can be preserved
 exactly rather than redesigned.

================================================================================
 2. THE CUT CRITERION
================================================================================

 DELETE code reachable only when one of these is configured:
   (a) a LogStorage            -- persistence, recovery, the fsync ticket
                                  FIFO, the async persistence threads
   (b) the ON-DISK side of snapshots only: FileSnapshotManager,
                                  MAKO_RAFT_SNAPSHOT_PATH, recovery of snapshots
                                  from disk at startup. Snapshots, log
                                  compaction and InstallSnapshot STAY, backed by
                                  the in-memory snapshot manager (owner's call).
   (c) a ReplicatedDB          -- the RocksDB-backed test state machine
   (d) the DURABLE ack tier    -- VoteDurable / AppendEntriesDurable RPCs,
                                  followerAckType, durableVoters_,
                                  durableAcks_, securedLeader_,
                                  CommitStatus::DURABLE,
                                  StepDownReason::SecuredFailure

 PRESERVE exactly the path taken when none of (a)-(d) is configured. Where a
 branch tested HasConfiguredStorage() / HasDurableStorage() /
 async_persistence_ / snapshot_manager_ / replicated_db_, the branch taken
 when they are false or null was kept and the other was dropped. Where a
 removed variable was compared against, its constant value was substituted
 first (snapidx_ == 0, securedLeader_ == false) and the expression simplified
 only when provably identical. Nothing was renamed: renames belong to the
 conversion.

 TWO FURTHER OWNER DECISIONS, taken during the cut:
   * Snapshots are memory logic in the Raft sense and stay. Only their
     on-disk implementation went. MAKO_RAFT_SNAPSHOTS=1 now constructs a
     MemorySnapshotManager; MAKO_RAFT_SNAPSHOT_INTERVAL still sets the
     threshold; MAKO_RAFT_SNAPSHOT_PATH is gone.
   * The two RaftServer friendships (RaftTestConfig, RaftLabTest) are
     removed. A public nested struct RaftServer::LabAccess, compiled only
     under RAFT_TEST_CORO, gives the harness one static accessor per private
     member it still needs. A nested class reaches the enclosing class's
     private members without friendship, and a Rust port expresses the same
     thing as a #[cfg(test)] module. The inert RaftCommo friendship of the
     generated RaftProxy is deleted outright.

 The MEMORY ack tier is NOT disk code and stays: memoryAcks_, specVoters_,
 specCommitIndex_, SPECULATIVE notifications, OnPeerRestart removing a
 restarted peer's memory vote and stepping down with UnsecuredFailure when
 the memory quorum is lost, and the ROLLEDBACK notifications that follow.
 That is the speculative design's memory half, and it is what production
 runs.

================================================================================
 4. WHAT SURVIVES WITH A NARROWER MEANING
================================================================================

 securedLogIndex_   Still assigned commitIndex when a node becomes leader and
                    0 when it steps down. Its only remaining role is the lower
                    bound of the UnsecuredFailure rollback range
                    (securedLogIndex_, lastLogIndex]. In memory-only Raft it
                    is "the commit index at leader start", not a durability
                    boundary. Name kept; comment added at the declaration.

 specCommitIndex_   Advances on memory-ack quorum and drives SPECULATIVE
                    notifications, exactly as before. Without a durable tier
                    it is the only notification tier.

 StepDownReason     UnsecuredFailure and HigherTerm remain. "Unsecured" now
                    simply means "a leader" -- every memory-only leader is
                    unsecured -- so the name is a fossil.

 CommitStatus       SPECULATIVE and ROLLEDBACK remain. DURABLE was never
                    emitted without storage and is gone. Consequence carried
                    over from the base branch: a pending commit callback is
                    erased only on DURABLE or on step-down, so in memory-only
                    mode pendingCallbacks_ entries live until leadership
                    changes. That is the base branch's no-storage behaviour,
                    preserved on purpose; see section 7.

 min_active_slot_   Advanced by the log retention window GC and by in-memory
                    log compaction after a snapshot, as before.

 unchanged. src/deptran/paxos/server.h holds a janus::raft::LogStorage and

 separate, mechanical change that touches Paxos and rrr; it was not done
 here.

 MakoCommandKind::ReplicatedDBCommand = 19 payload registration inside its
 DSL block. The kind number stays reserved on purpose (wire compatibility);
 the forward declaration compiles without the class.

 7. DECISIONS THE OWNER SHOULD CONFIRM
================================================================================

 D1. Should SPECULATIVE be terminal in memory-only mode? Today a commit
     callback is notified SPECULATIVE on memory quorum and then left
     registered until step-down (it used to be erased on DURABLE). Nothing in
     Mako production registers commit callbacks (the only caller was the
     deleted ReplicatedDB), so this only affects RaftLab tests 63/64 and
     future users of StartWithCallback. Preserved as-is here.

 D2. Should the shared storage headers move out of src/deptran/raft?
     See section 5.

 D2b. LabAccess hands out references to private fields, so the harness can
     still mutate server state directly (membership tests seed match_index_
     and next_index_ that way). That mirrors what the friendships allowed. If
     the conversion wants a read-only inspection surface, the mutating
     accessors are the list to shrink.

 D3. Rename the fossil names during conversion (securedLogIndex_ ->
     leader start commit index; StepDownReason::UnsecuredFailure ->
     MemoryQuorumLost; specVoters_/specCommitIndex_ keep "spec" or become
     plain voters/commit)? Not done here by design.

 D4. Tests 16-18 (partition-plus-restart) exercised the NotifyRestart retry
     path and asserted nothing persistence-specific, but the base ran them
     only in the persistence arm, so they went with it. If NotifyRestart
     retry coverage is wanted in the memory-only lab, they can be restored
     as memory-only tests: a restarted node comes back empty and catches up
     by replication or InstallSnapshot, which they already tolerated.

 D5. The two-tier design will need to come back for production durability.
     This branch is the memory core it will be layered on; the base branch
     codex/raft-stage2-prep keeps the full implementation and its 155-case
     matrix as the reference.

================================================================================

 1. Run the Docker Raft CI suites against this branch on a host with Docker:
    shard1ReplicationRaft, shard2ReplicationRaft and the Simple variants.
    They drive the production memory path end to end through Mako; RaftLab
    drives it through the harness. Both green closes the preservation
    argument.
 2. Decide D1-D4 in section 7. D1 (is SPECULATIVE terminal?) is the one that
    changes code.
 3. Start the conversion on the reduced surface: 90 predicates in server.h,
    32 DSL blocks, 17 crate modules, 38 files. The two Stage 2 gates still
    apply unchanged -- Q1b (no ODR post-pass for raft carriers, so header
    types with methods do not link) and Q1c (a pub trait is not a drop-in
    for a pure-virtual class). Six pure-virtual interfaces became two:
    LogStorage and its storage siblings left RaftServer's reach, leaving
    SnapshotManager, SnapshotReader/Writer, TransportBase and DispatcherBase.
 4. The disk side comes back later as a layer on this core. The base branch
    codex/raft-stage2-prep holds the full two-tier implementation and its
    155-case matrix as the reference for that work.
 5. Documentation outside src/ still describes the deleted mechanisms
    (docs/raft-book.md sections 11-12 in part,
    docs/raft-restart-and-ownership.txt
    section 4 on friends, docs/plans/log-persistence/*, docs/stage2_raft.txt).
    They are correct for the base branch and were left alone; this file is
    the record for the memory-only branch.
