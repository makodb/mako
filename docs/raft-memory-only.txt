 1. WHY THIS BRANCH EXISTS
================================================================================

 The Rust conversion recorded in docs/stage2_raft.txt stalled on two gates,
 and its data-structure classification put the whole memory-versus-durable
 two-tier design in Class A, "on the boundary, do not convert without
 review". The owner's decision was to convert the in-memory consensus first
 and bring durability back afterwards. This branch produces that smaller
 codebase.

 Two facts make the reduction safe rather than speculative.

 First, production Mako never configured a LogStorage, a SnapshotManager on
 disk or a ReplicatedDB. Those were opt-in through environment variables read
 in RaftServer::SetupInternal, and no example script, CI script or config
 file sets them. Only the RaftLab harness and the retired persistence test
 arms turned them on.

 Second, production Mako calls exactly eight RaftServer methods:

   EnsureSetup   Start   WaitForStartup   IsLeader
   GetLeaderHint   RegisterLeaderChangeCallback   PrepareForShutdown
   SetPreferredLeader

 All eight survive with unchanged behaviour, and RaftStartResult keeps
 {REJECTED = 0, APPENDED = 1}. Everything removed was either unreachable in
 production or reachable only through a fault this branch's model excludes.

================================================================================
 2. THE FAULT MODEL, AND WHAT IT IMPLIES
================================================================================

 Fixed by the owner:

   * the network can partition;
   * a server's memory is a disk that never fails;
   * a server never crashes and never restarts.

 Three consequences drive the whole cut.

 NO DURABILITY TIER. The original design acknowledged a vote or an append
 twice, once from memory and once after fsync, and published a commit only
 after the durable acknowledgement. With memory that never fails, the two
 acknowledgements carry identical weight, so the distinction classifies
 nothing. Commit is the textbook match-index majority in the current term.

 NO RESTART MACHINERY. Restart detection, recovery, and the plumbing that let
 an in-flight RPC handler survive a swapped RaftServer all handle a fault
 that cannot occur.

 NO EXTENSIONS RAFT DOES NOT NEED. Leadership transfer and membership change
 are not required for safety or liveness under partitions alone. Snapshots
 are not required either, but the owner chose to keep them, so log compaction
 and InstallSnapshot stay, backed by an in-memory snapshot manager.

 What remains is textbook Raft with in-memory snapshots, plus one
 Mako-specific timer policy: the preferred-leader election bias, which
 production configures and therefore must keep working.

 3. THE RPC SURFACE
================================================================================

 src/deptran/rcc_rpc.rpc, service Raft, declares four RPCs:

   Vote                 leader election
   AppendEntries        log replication
   EmptyAppendEntries   the heartbeat variant, same reply shape
   InstallSnapshot      catch-up for a follower behind the compaction point

 Down from ten. Every surviving rpc id is unchanged, because rpcgen freezes
 ids by reading the committed header back on each regeneration; renaming a
 method would be a wire break rather than a refactor. Only
 EmptyAppendEntries changed shape, losing the trigger_election_now input that
 piggybacked leadership transfer.

 5. WHAT IS KEPT
================================================================================

 5.1 CONSENSUS

 Elections with the preferred-leader timer bias and its grace-period knobs
 MAKO_RAFT_PREFERRED_GRACE_US, MAKO_RAFT_NONPREFERRED_GRACE_ELECTION_MIN_US
 and _MAX_US; the HeartbeatLoop replication engine with its batching and its
 per-follower backoff; commit on the match-index majority with the
 current-term check; the apply thread with EnqueueCommittedEntries,
 PublishAppliedIndex and the learner action callback; leader-change
 callbacks; GetLeaderHint; the RequestReplication wake gate that lets a
 client submission wake the heartbeat fiber early; the log retention window
 GC and min_active_slot_.

 5.2 SNAPSHOTS, IN MEMORY

 snapshot_manager.hpp, memory_snapshot_manager.hpp and snapshot_format.hpp;
 snapshot_manager_, snapidx_ and snapterm_; InitializeSnapshotManager;
 CreateSnapshot, MaybeCreateSnapshot and CreateSnapshotLocked; CompactLog;
 Set and GetSnapshotThreshold; HasSnapshot, GetSnapshotIndex and
 GetSnapshotTerm; the InstallSnapshot RPC end to end with OnInstallSnapshot
 and the HeartbeatLoop branch that sends it to a lagging follower;
 install_snapshot_callback_gate_ and AsyncCallbackLifetime, which keep an
 InstallSnapshot reply callback from outliving the server; the generic
 state-machine snapshot hooks; every snapshot and compaction predicate.

 MAKO_RAFT_SNAPSHOTS=1 now reuses a manager already installed through
 SetSnapshotManager, restoring its latest boundary, and otherwise constructs
 an empty MemorySnapshotManager. MAKO_RAFT_SNAPSHOT_INTERVAL still sets the
 threshold. MAKO_RAFT_SNAPSHOT_PATH is gone. This reuse rule is the one
 snapshot behaviour that is not a pure projection of the base, where a fresh
 FileSnapshotManager always overwrote an injected one, and a Rust port must
 reproduce it.

 5.3 THE RPC TEARDOWN BARRIER

 At the base, every handler held a ServerLease, and both the service
 destructor and RaftWorker::ShutDown closed admission and waited for admitted
 handlers to leave before the RaftServer was freed. Removing the leases
 dropped that barrier, which review caught: on the ordinary shutdown path an
 executing handler could dereference a freed RaftServer. That is a fault the
 model does not excuse, since it is orderly teardown rather than a crash.

 The barrier is restored using rrr's own mechanism rather than a new lease
 type. RaftWorker::ShutDown and destroy_stub_servers now call
 set_admission_ready(false) followed by drain(), before PrepareForShutdown,
 matching the base's order. The drain has a 5000 ms ceiling that warns and
 names the residual pending count, where the base waited without bound. Both
 call sites run on native threads, so the drain's sleep cannot stall a poll
 thread.

 5.4 THE HARNESS

 Disconnect, Reconnect and IsDisconnected, which are how RaftLab simulates
 partitions, and the RPC counting. RaftServer::LabAccess survives with 11
 accessors, each with a live caller: stop, state_machine_apply_mtx,
 is_leader, vote_for, current_leader_id, req_voting, election_in_progress,
 snapidx, snapterm, snapshot_manager and CreateSnapshotLocked.

 5.5 KEPT DESPITE LOOKING LIKE FOSSILS

 Two predicates named for ReadIndex, raft_server_read_index_round_can_advance
 and raft_server_read_index_reply_confirms_authority, keep live callers in
 HeartbeatLoop, and the authority-rounds machinery they serve is not ReadIndex
 bookkeeping: it breaks the response-poll loop as soon as a majority has
 replied. Removing it would make every heartbeat round wait for the full
 response deadline, which is a real latency change. So heartbeat_round_,
 read_quorum_confirmed_term_, read_quorum_confirmed_round_,
 PendingHeartbeatAuthority and PendingAppendEntries::sent_round survive, and
 their [READ-INDEX] log tags were left alone, consistent with not renaming
 surviving members.

 AmIPreferredLeader survives because GetElectionTimeout calls it, and
 production reaches that through SetPreferredLeader.

 RaftCommo's vote quorum lost the mutex that had also serialized its
 highest-term read-modify-write. That is not a race: the only caller of
 FeedResponse is the vote reply callback, which rrr decodes inline on the one
 poll thread, and the candidate reads the term from a fiber on that same
 thread. rusty::Cell is the correct primitive for single-threaded interior
 mutability, and the neighbouring vote counters were already plain Cells.

 8. OPEN ITEMS FOR THE OWNER
================================================================================

 O1. Run the Docker Raft CI suites where Docker exists. This is the only
     material gap in the verification.

 O2. Should the three shared storage headers move out of src/deptran/raft?
     See section 6.

 O3. ReadIndex was removed as an API production does not call, which the
     owner confirmed. Note that it is the linearizable-read helper for a
     partitionable network, so it is the one removal this fault model does
     not itself justify. The state it needed was retained for the heartbeat
     authority machinery (5.5), so restoring it later is cheap.

 O4. RaftServer::RequestVote() now has no caller.
     RequestVoteFromElectionTimer is the only live entry into
     RequestVoteImpl, and there is no TxLogServer::RequestVote for it to
     override. Deleting it is safe; it was left because it was outside the
     cut's scope.

 O5. ServerWorker::ShutDown in src/deptran/server_worker.cc deletes its RPC
     server without the drain added in 5.3. It is not the freed-server
     window that review caught, since ServerWorker explicitly does not
     delete its scheduler, and the file is shared with Paxos, so fixing it
     would step outside this branch. Worth a look on its own.

 O6. server.h no longer names rusty::Mutex, rusty::Condvar, rusty::thread or
     ViewData, so two includes are unused and ../view.h now supplies only
     epoch_t and View. The include list was left alone.

 O7. Documentation outside this file still describes the removed mechanisms:
     docs/raft-book.md sections 11 and 12, docs/raft-restart-and-ownership.txt
     section 4 on the friend declarations, docs/raft-rpc-flow.txt on the ten
     RPCs, docs/plans/log-persistence/, and docs/stage2_raft.txt. All are
     accurate for codex/raft-stage2-prep and were left alone. This file is
     the record for this branch.

 O8. Fossil names survive where renaming would have violated the
     preservation rule: the [SPEC-RAFT] log tags in stepDown, the
     [READ-INDEX] tags described in 5.5, and 'Unsecured' nowhere, since
     StepDownReason is gone. Renaming belongs to the Rust conversion.
