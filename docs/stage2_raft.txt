 1. WHAT STAGE 2 IS, AND WHAT IT IS NOT
================================================================================

 Per docs/migration/rustycpp/raft-rust-migration.md the path is:

   existing C++
     -> inline Rust DSL with adjacent generated C++      (Stage 1)
     -> exact mechanical Rust extraction                 (Stage 2)  <-- HERE
     -> whole-provider dual-compile canary               (Stage 3)
     -> canonical .rs with build-tree-generated C++      (Stage 4)

 Stage 2 does NOT change what ships. Line 84 of that doc: "Production still
 uses the adjacent generated C++ during this stage." The inline blocks remain
 the single source of truth; the crate is a derived VERIFICATION view.

 So after Stage 2 the code is still Rust blocks + generated C++, plus a crate
 whose .rs files are generated by concatenating those blocks. Three
 representations, two of them the same Rust, kept honest by a hash-drift
 check. The duplication only resolves at Stage 4, which deletes carriers one
 at a time. src/rrr shows the end state: 37 canonical .rs modules, C++
 generated into the build tree, and only 5 files still carrying inline blocks.

 THE OWNER'S DECISION (settled, do not re-litigate): verification moves from
 a per-carrier bare-rustc compile to crate-level rustc + clippy, matching
 src/rrr. This was "Option B".

 2.2 AN ODR VIOLATION, FIXED (4e427f74)
--------------------------------------------------------------------------------
 log_storage.hpp and snapshot_manager.hpp each redeclared slotid_t and
 ballot_t behind #ifndef guards as UNSIGNED, while constants.h:6 spells
 ballot_t as SIGNED int64_t. Neither header included constants.h, so the type
 each declared depended on include order.

 Measured with clang -E using real compile_commands.json flags: of the 18 TUs
 that transitively include either header, 16 saw constants.h first and 2 did
 not --

   tests/legacy_raft_log_test.cc           log_storage.hpp at .i line 99874,
                                           constants.h only at 160777
   tests/raft_memory_snapshot_manager_test.cc
                                           constants.h never included

 Both got ballot_t = uint64_t. The cause in the first was a two-line accident:
 line 8 includes log_storage.hpp, line 9 includes tpc_command.h which reaches
 constants.h via __dep__.h:120. Swapping those two source lines silently
 changed LogEntry::term's signedness, and the build uses -w so nothing warned.

 The consequence was a real ODR violation: server.cc.o and
 legacy_raft_log_test.cc.o both defined the weak comdat symbol
 janus::raft::LogEntry::load(BinaryReadArchive&) compiled against different
 field types, both were linked into build/test_legacy_raft_log, and the linker
 kept one. Member types are not mangled, so nothing detected it.

 Benign so far only because i64/u64 are layout-identical, both rrr serializers
 are raw 8-byte memcpy, and the DSL blocks in those headers write plain
 uint64_t and never name the alias.

 FIX: include ../constants.h, delete the guarded redeclarations.
 PROOF: the two LogEntry::load bodies are now byte-for-byte identical (84
 instructions each, llvm-objdump). Before, they differed.

 Q1b. Should raft_dsl.sh get its own ODR post-pass?
      THIS GATES ALMOST ALL OBJECT CONVERSION.
--------------------------------------------------------------------------------
 Corrects an earlier claim of mine. The bare-rustc gate was NOT the only thing
 forcing free-functions-over-scalars. raft_dsl.sh:4-5, verbatim:

   "Unlike scripts/regen_storage_dsl.sh, Raft carriers do not receive an ODR
    or textual post-pass: the pinned transpiler's output is committed
    byte-for-byte."

 regen_storage_dsl.sh:89-96 is the pass raft lacks -- a regex prefixing
 `inline ` onto column-0 out-of-line definitions inside GEN regions.

 Proven by link test: a header-resident type with methods emits its ctor and
 methods out-of-line, so two TUs including that header both define them:

   /usr/bin/ld: odr_b.o: multiple definition of
     'janus::raft::RaftSubmissionProgress::RaftSubmissionProgress()';
     odr_a.o: first defined here

 ODR-EXEMPT SHAPES (safe today): pub trait (dtor emitted in-class); struct
 with no impl; pub const fn (constexpr => implicitly inline).

 OPTIONS
  (a) give raft_dsl.sh a raft-local ODR pass -- unlocks methods on header
      structs, i.e. most of what Stage 2 was meant to buy. CLAUDE.md says
      regen_storage_dsl.sh's pass is specific to those headers, so this must
      be a separate implementation, not reuse.
  (b) restrict conversions to ODR-exempt shapes (what I did overnight).
  (c) only convert types defined in .cc files -- very few qualify.

 Related, already solved: #[cpp_ctor] does not compile under the crate gate
 ("cannot find attribute cpp_ctor"); the working spelling is
 #[cfg_attr(any(), cpp_ctor)], the inert-marker idiom already live at
 messages.hpp and commo.h:226. clippy also rejects a bare fn new() via
 clippy::new_without_default.

 Q1c. pub trait is NOT a drop-in for a pure-virtual class -- verified
--------------------------------------------------------------------------------
 I was one step from converting the six pure-virtual interfaces
 (LogStorage 18 methods, SnapshotManager 10, TransportBase 9, DispatcherBase
 8, SnapshotReader/SnapshotWriter 4 each) on the basis that a trait renders
 byte-identically and so cannot change behaviour. I probed it. That is FALSE.

 For SnapshotWriter the transpiler emits:

   class SnapshotWriter {
   public:
       virtual ~SnapshotWriter() noexcept(false) {}      // (1)
       virtual bool Write(const int8_t* data, size_t size) = 0;
       ...
       SnapshotWriter(const SnapshotWriter&) = delete;   // (2)
       SnapshotWriter& operator=(const SnapshotWriter&) = delete;
       SnapshotWriter(SnapshotWriter&&) = delete;
       SnapshotWriter& operator=(SnapshotWriter&&) = delete;
   protected:
       SnapshotWriter() = default;
   };
   template <class U> class SnapshotWriterAdapter;        // (3)
   template <class U> class SnapshotWriterAdapterRef;
   template <class U> class SnapshotWriterAdapterRefMut;

 Three differences from the incumbent at snapshot_manager.hpp:119 --
  (1) EXCEPTION SPECIFICATION CHANGES. Incumbent is
      `virtual ~SnapshotWriter() = default;`, implicitly noexcept(true). The
      generated form is noexcept(false). That flips
      std::is_nothrow_destructible_v and relaxes a guarantee derived classes
      were compiled under; FileSnapshotWriter::~FileSnapshotWriter() override
      (file_snapshot_manager.hpp:307) is one of them.
  (2) Deleted copy and move are added. The incumbent declares none.
  (3) Three adapter templates are added that do not exist today.

 I did NOT test whether this breaks the build -- that needs a production build
 of a live storage interface, which I would not do unattended. But the premise
 is false, so the trait route needs either an emitter option matching the
 incumbent destructor, or an accepted reviewed ABI delta. rustc also rejects
 the C++ method names, so each trait needs #[allow(non_snake_case)].

 RECOMMENDATION: do not convert any of the six until this is settled.

 Q1a. Is "secured" monotonic for the life of a term?
--------------------------------------------------------------------------------
 raft_server_should_become_secured takes `already_secured` and is latching
 (!already_secured && durable_vote_count >= quorum), which reads as "once
 secured, always secured". If that is a genuine invariant rather than an
 optimisation it deserves a static_assert or a comment, because a future
 conversion could drop the guard and no test would notice.

--------------------------------------------------------------------------------
 Q2. ReplicatedDBOp -- what should decoding do with an invalid byte?
--------------------------------------------------------------------------------
 replicated_db.h:28 is #[repr(u8)] with PUT=1 DELETE=2 BATCH=3. The migration
 doc records that Stage 1 owns it only because the emitted C++ still accepts
 every raw u8 including unnamed values, that a real Rust enum cannot, and that
 KVOperation is transiently value-created with ZERO -- which is not a valid
 variant. Promoting it needs a decode contract decision.
   (a) transparent byte newtype + named constants -- behaviour-preserving,
       loses exhaustiveness. My default if asked.
   (b) real enum + TryFrom<u8> rejecting invalid -- safer, changes behaviour
       for malformed input that may be reachable from disk.
   (c) real enum with explicit UNKNOWN = 0 -- changes the persisted meaning
       of zero.

--------------------------------------------------------------------------------
 Q3. Wrapping arithmetic in the snapshot-size guards -- preserve or harden?
--------------------------------------------------------------------------------
 The snapshot parser deliberately uses wrapping addition at the incumbent
 size_t/uint64_t widths; the migration doc says overflow hardening "must be a
 separate correctness change before native Rust executes this parser". Rust
 panics on overflow in debug and wraps in release, so writing these in Rust
 means choosing wrapping_* (preserve) or checked_* (harden). Hardening is a
 behaviour change on malformed input in a parser reading attacker-influenced
 bytes from disk. I would preserve with explicit wrapping_* and a TODO.

--------------------------------------------------------------------------------
 Q4. The legacy non-IEEE CRC32 table -- confirm it stays as-is
--------------------------------------------------------------------------------
 The production table contains legacy non-IEEE entries; tests pin the existing
 checksum bytes because correcting it would change every persisted snapshot,
 and the doc says a fix requires a separately versioned format change. This
 does not block converting the CRC32 object -- only anyone who thinks the
 table is a bug. Assuming yes, leave it.

--------------------------------------------------------------------------------
 Q5. Schema 1 or 2 for the raft manifest?
--------------------------------------------------------------------------------
 Built as schema 1 (extraction), which the migration doc specifies and which
 is additive and reversible: blocks stay authoritative, production unchanged.
 Schema 2 (canonical .rs, carriers deleted, C++ generated into the build tree)
 changes what production compiles. Confirm schema 1 is wanted.

--------------------------------------------------------------------------------
 Q6. What happens to the 39-entry EXPECTED_BLOCKS ratchet?

 RaftSubmissionProgress) and fails if it does not match. Good anti-drift, but
 every conversion now edits both it and the crate manifest -- two inventories
 to keep in sync. Keep both, derive one from the other, or drop the ratchet?
 Kept both for now; revisit at Stage 3.

 Q8. Is /tmp acceptable for the persistence tests?
--------------------------------------------------------------------------------
 /tmp on this host is TMPFS, so fsync() never reaches stable storage.
 Crash-RECOVERY is genuinely tested (tmpfs survives process death); durability
 against machine failure is not tested at all. The async arm in particular
 exists to defer durable acknowledgement, so passing it on tmpfs proves the
 memory-vs-durable BOOKKEEPING and not the durability. Pointing
 MAKO_RAFT_PERSISTENCE_PATH at real local disk would fix it, but I have not
 confirmed this host has non-tmpfs local scratch (/home is NFS).

--------------------------------------------------------------------------------
 Q9. A documentation bug, deliberately NOT fixed
--------------------------------------------------------------------------------
 server.h:82, in the StepDownReason doc comment, describes the SecuredFailure
 suspect range as:

   *   Only unsecured entries (specCommitIndex, securedLogIndex] are suspect.

 The bounds are REVERSED. The invariant at server.h:2347 is
 securedLogIndex_ <= specCommitIndex_, so that interval is empty. The suspect
 entries -- memory-acked but not yet durable -- are
 (securedLogIndex_, specCommitIndex_]. The code appears correct; the comment
 is wrong. It sits in a Class A doc block, so it wants owner confirmation of
 the intended reading rather than my guess.
