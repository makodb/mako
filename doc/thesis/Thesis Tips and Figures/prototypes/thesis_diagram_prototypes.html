Mako Raft Thesis Diagram Prototypes

These are drawing prototypes, not final artwork. Use them as layout and content baselines for manual redraws in Figma, PowerPoint, Keynote, or draw.io. The diagrams only express claims already present in the thesis.

Figure 1: Original Mako Paxos Replication Path

Baseline before Raft: leader-side workers generate transaction logs; Multi-Paxos establishes committed order; followers replay logs.

Caption draft: Original Mako replication path. Leader-side Mako worker threads execute transactions and submit serialized transaction logs through a common replication interface. The original backend, Multi-Paxos, establishes the committed log order, which follower replicas replay into their local database state.

Figure 2: Paxos, Multi-Raft, and Single-Raft Topologies

Design comparison: Multi-Raft preserves Paxos-style parallel streams; Single-Raft consolidates commands into one Raft log.

Caption draft: Replication topologies evaluated in this thesis. Multi-Raft keeps the per-partition replication shape of the original Paxos design, whereas Single-Raft consolidates all partition commands into one Raft log.

Figure 3: Preferred Leader Election for Mako

Mako submits transactions through one expected local leader; preferred leader election keeps Raft aligned with that path while preserving failover.

Caption draft: Preferred leader election aligns Raft leadership with Mako's leader-oriented submission path. The preferred replica is favored during startup and safe failback, while ordinary Raft failover remains available.

Include: Mako workers, preferred leader, backup replicas, normal log replication, failover/failback behavior, and a safety note. Avoid: detailed Raft RPC names, election state machines, timeout constants, and anything that makes preference look like a new consensus protocol.

Figure 4: Single-Raft Replay Bottleneck Before ReplayPool

Many workers feed one Raft log; without replay offload, follower replay can lag behind committed work.

Caption draft: Naive Single-Raft consolidation risks a replay bottleneck: many workers feed one ordered log, but expensive follower replay can accumulate behind a narrow apply/replay path, so leader-side throughput alone can hide follower replay lag.

Figure 5: Final ReplayPool Pipeline

The final design keeps Raft apply lightweight and parallelizes heavy follower replay with ReplayPool workers.

Caption draft: Final Single-Raft replay pipeline. The Raft apply path stages committed payloads, while ReplayPool workers perform heavy follower-side replay in parallel.

Figure 6: Persistence and Simulated-Disk Proof Path

Disk experiments are defensible because the simulated disk reports per-source bytes, write counts, and normalized storage work.

Caption draft: Source-tagged simulated-disk instrumentation. Persistence writes are charged to a simulated disk model and reported as bytes, writes, bytes per committed transaction, and source breakdowns, allowing disk throughput changes to be explained with measured storage work.
