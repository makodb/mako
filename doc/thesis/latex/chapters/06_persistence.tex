\chapter{Persistence and Simulated Disk}

The earlier chapters explained how Mako produces transaction log records, how
Raft orders those records, and how followers replay them. This chapter explains
what happens when the experiment also asks the replication backend to pay a
storage cost.

The basic idea is simple. A replicated system should not only send committed
records to other replicas; it should also remember enough information on stable
storage to recover after a crash. For Raft, that durable information includes
the replicated log, the current term, and voting metadata. The replicated log
tells a restarted replica what records were accepted. The term and vote
metadata prevent the replica from forgetting earlier election decisions.

The thesis does not try to prove that the implementation is a complete
production storage stack. Instead, it asks a narrower evaluation question: when
storage persistence is enabled, how much modeled disk work does each backend
generate? That question matters because a disk-throughput curve is hard to
defend without proof of the storage work behind it.

\section{Why Use a Simulated Disk}

Real storage devices differ a lot. A local NVMe drive, a cloud block device,
and a cloud SSD volume can have different latency, bandwidth, queueing, and
writeback behavior. If the thesis used one physical device directly, a result
could be caused by that specific device rather than by the replication backend.

To keep the comparison controlled, the evaluation uses a simulated disk. The
simulated disk charges each persistence operation for two costs:

\begin{itemize}
  \item a fixed latency cost for issuing a write, and
  \item a bandwidth cost based on how many bytes are written.
\end{itemize}

For a write of size \(B\) bytes, the simulator charges a service time equal to
the fixed latency plus the time needed to transfer \(B\) bytes at the configured
bandwidth. The model also queues writes, so later writes can wait behind
earlier writes. This is important because a storage device is not just a
per-write delay; it is also a shared resource when many threads issue writes.

The source breakdown needs one more explanation. Mako transaction-data writes
are the serialized transaction records produced by leader-side execution. Raft
log writes are the consensus records that let Raft recover the ordered history.
Raft metadata writes are smaller records such as term and vote state. The
evaluation does not treat all of these as one black-box number; it records them
separately so the disk results can be explained.

\section{Why These Counters Are Needed}

The disk results in Chapter 8 show that the Cloud-SSD-like model flattens at
high worker counts. Throughput alone is not enough to explain that behavior.
If a graph flattens but the system did not actually write much data, the result
could be a benchmark artifact. If the graph flattens while the simulated disk
records comparable bytes, comparable writes, and comparable bytes per
transaction across backends, then the interpretation is stronger: the storage
model was doing real measured work.

This is why the thesis reports both throughput and simulated-disk counters.
Throughput says how fast the benchmark completed committed transactions. The
storage counters say how much modeled persistence work was charged while doing
that work.

\section{Scope of the Claim}

The persistence claim is intentionally limited. The thesis shows that, under a
controlled simulated-storage model, the disk-throughput curves are backed by
measured bytes and writes. It does not claim that every production SSD,
filesystem, or cloud block device will produce the same absolute throughput. It
also does not replace a full crash-recovery certification effort. Within this
scope, the simulated disk is still useful because it lets the evaluation
compare the replication backends under repeatable NVMe-like and Cloud-SSD-like
pressure.
