\chapter{Preferred Leader Election for Mako}

Chapters 2 and 3 established that the Raft backend must fit an existing
Mako execution model. Mako's worker threads run on a leader-side process,
produce transaction log records, and submit those records into the replication
layer. Follower processes receive committed records and replay them into their
local state. The original Mako/Paxos path fit this shape naturally because the
leader-side role was fixed by the benchmark and deployment setup. There was no
independent Raft-style election that could move the active submission role to a
different process.

Raft changes that assumption. In ordinary Raft, any replica with a safe enough
log may become leader if it wins an election. That is correct for Raft, but it
creates a placement problem for Mako: the process that Raft chooses as leader
must line up with the process where Mako is submitting transaction work.
Preferred leader election is the mechanism used in this thesis to solve that
integration problem. It is not a new consensus protocol. It is a leader-placement
policy around Raft that makes Raft leadership compatible with Mako's
leader-oriented transaction submission path while preserving ordinary Raft
safety and failover behavior.

\section{The Placement Problem}

Consider the three-replica setup used throughout this thesis: one submission
replica and two backup replicas. In the benchmark configuration, the submission
replica is the process that runs the throughput-producing Mako worker threads.
Those workers execute transactions, serialize the resulting transaction log
records, and submit the records into the local replication backend. The backup
replicas are follower replicas in the normal case. They receive the committed
records and replay them into their own database state.

This arrangement is not an accident of naming. It is part of how the Mako
benchmark path is organized. The local process is the one producing the
leader-side work whose throughput is reported. The follower processes are the
evidence that the committed work is replicated and replayable elsewhere. In the
original Paxos integration, this did not require a separate leader-placement
mechanism because the Paxos path was wired around that fixed leader-side role.
Mako submitted work through the expected process, and the comparison did not
depend on a separate election choosing among replicas with different Mako roles.

This is also why the issue cannot be solved by simply letting Raft elect any
safe leader and leaving the rest of Mako unchanged. The benchmark workers run in
the leader-side submission role, and the transaction log records they generate
enter the replication layer through the local backend attached to that role.
The integration does not include a second path that moves workload generation
or forwards every generated log record to whichever remote replica Raft happens
to elect.

With Raft, the same setup has a new degree of freedom. Standard Raft is allowed
to elect either backup replica if that replica is eligible and can obtain a
majority. From Raft's point of view, such a leader can be perfectly safe. From
Mako's point of view, however, it is the wrong placement for the normal
benchmark path. The Mako workers on the submission replica would be submitting
transaction log records to a local replica that is not the Raft leader. A
non-leader replica cannot accept those records as the source of a new committed
log order, so the run would no longer measure the intended leader-side
Mako/Raft pipeline.

The issue is therefore not that Raft elects unsafe leaders. The issue is that
Raft's default election policy is unaware of Mako's role assignment. Mako needs
the leader-side submission process and the Raft leader process to be the same
replica during the normal case. Preferred leader election makes that placement
choice explicit.

\section{Why Mako Needs Preferred Leadership}

Preferred leadership is required by the Mako/Raft integration, not by Raft
correctness. A standalone Raft service can usually accept client requests at
whichever replica is currently leader, or it can redirect clients to that
leader. Mako's benchmark path is more structured. As described in Chapter 2, the
worker lanes on the leader-side process execute transactions and produce log
records. As described in Chapter 3, the Raft backend sits behind Mako's existing
replication boundary. The local Mako workers expect that boundary to lead to a
leader-side replication path.

This requirement applies to both Raft topologies evaluated in the thesis. In
Multi-Raft, each worker-lane partition has its own Raft group, and the local
replica of each group must be the normal leader for that lane's transaction
submissions. In Single-Raft, all partition commands share one consolidated Raft
log, and the local replica of that consolidated group must be the normal leader
for all worker-lane submissions. Single-Raft later needs ReplayPool to keep
follower replay from becoming the bottleneck, but both Multi-Raft and
Single-Raft need preferred leadership to align Raft with Mako's leader-oriented
submission path.

The mechanism also makes the evaluation fairer. The goal is to compare Paxos,
Multi-Raft, and Single-Raft as replication backends for the same Mako execution
pipeline. If Raft leadership lands on a follower process while Paxos uses the
fixed leader-side process, the experiment is no longer comparing equivalent
paths. Preferred leader election removes that accidental difference. It lets the
Raft runs use the same leader-side execution and submission role that the Paxos
runs use.

\section{Design: Preference, Not Authority}

The design principle is preference, not authority. The preferred replica is the
replica that should lead in the normal case because it is where Mako submits
leader-side transaction work. Preference does not give that replica permission
to ignore Raft's rules. It only biases leadership placement toward the replica
that matches Mako's execution model.

Figure~\ref{fig:preferred-leader-election} shows the normal arrangement. Mako
workers submit transaction log records to the preferred leader, which is the
submission replica in the normal case. That leader replicates the Raft log to
the backup replicas. The backup replicas are not passive storage devices: they
remain ordinary Raft replicas that can participate in elections and can lead if
the preferred replica is unavailable. The figure is intentionally about
placement. It shows where leadership should live in the common case, not a new
set of consensus rules.

This distinction matters during failures. If the preferred replica is
unavailable, the system should not stop merely because the normal submission
replica cannot lead. Raft availability still comes from allowing a majority of
replicas to elect a leader. In that case, a backup replica may become leader
using the ordinary Raft election rules. When the preferred replica later
returns, preference can help move leadership back only after the returning
replica is safe enough to lead. The preferred replica does not become leader
simply because it has a preferred label.

\section{Mechanism}

The mechanism can be understood as three phases: startup bias, failover, and
safe failback.

At startup, the Raft configuration marks the Mako submission process as the
preferred replica for each relevant Raft group. For Multi-Raft, that means the
local replica is preferred for each worker-lane Raft group. For Single-Raft,
that means the local replica is preferred for the consolidated Raft group. The
purpose is to make the normal startup case choose the same process that Mako
uses for leader-side transaction execution and log submission.

This startup preference is deliberately limited. The preferred replica is not
given a permanent shortcut that lets it win every later election. After the
startup placement phase, the replicas return to ordinary Raft election
behavior. This keeps preference from turning into authority: the preferred
label explains where leadership should live in the healthy common case, but it
does not remove Raft's voting or log-freshness requirements.

During failover, preference gives way to availability. If the preferred replica
is unavailable, the backup replicas continue to run ordinary Raft elections.
They can vote, win leadership, replicate entries, and commit records according
to Raft's normal rules. This is important because a leader-placement policy that
prevented backups from leading would make the system less available than Raft
itself.

Safe failback handles the opposite direction. Suppose a backup replica is
currently leader because the preferred replica was unavailable. When the
preferred replica returns, the backup leader cannot simply hand over leadership
immediately. First, the current leader must observe that the preferred replica
has caught up with the log the leader is responsible for preserving. In simple
terms, the preferred replica must already have the history it would need in
order to lead safely. Once that condition holds, the current leader can send a
best-effort transfer hint through the normal Raft communication path. The
preferred replica must still become leader through Raft's election rules; the
hint does not install it as leader by itself.

This mechanism is deliberately modest. It does not add a second leader role and
does not create a special path for client commands. It only makes leader
placement cooperate with Mako's existing execution structure.

\section{Safety Boundary}

Preferred leader election changes placement policy, not consensus safety. The
ordinary Raft safety rules remain the boundary around the mechanism. A replica
still grants at most one vote in a term. Terms still identify newer leadership
attempts and prevent older leaders from continuing after they are superseded.
Candidates still have to satisfy Raft's log up-to-date voting rule. Committed
entries still require majority replication. A preferred replica that is stale
cannot safely become leader merely because it is preferred.

The catch-up condition is the key engineering guard for failback. The current
leader should attempt transfer only when it believes the preferred replica has
the committed prefix of the log. That condition does not replace Raft's election
rules; it prevents the implementation from encouraging a stale replica to seek
leadership. If the preferred replica is behind, if the transfer hint is lost, or
if another election happens first, the system falls back to ordinary Raft
behavior.

This is why the chapter's claim is narrow. Preferred leader election makes Raft
usable in Mako's leader-oriented submission model. It does not make Raft safer,
and it does not weaken Raft to obtain placement.

\section{What It Does Not Claim}

Preferred leader election should not be read as a stronger protocol than it is.
It does not promise that the preferred replica is always leader. It does not
bypass voting, term checks, or log freshness checks. It does not make a stale
preferred replica safe to lead. It does not replace normal Raft failover. It
also should not be read as an exhaustive evaluation of every production failure
mode. The implemented and tested recovery path covers preferred-replica
absence, backup leadership, preferred catch-up, and safe failback; broader
crash, storage, and network-fault campaigns are outside this thesis.

Those limits are important for the thesis argument. The contribution is not
``Raft with a new safety rule.'' The contribution is a Mako-specific integration
mechanism: keep ordinary Raft failover available, but bias normal leadership
toward the process where Mako can actually submit leader-side transaction work.

\section{Validation}

The validation evidence for preferred leader election is placement and
integration evidence rather than a new headline throughput graph. The tests
exercise both Raft topologies because the mechanism is used by both Multi-Raft
and Single-Raft. A separate no-regression sweep then checks that the added
placement and failback logic does not change the expected throughput shape.
