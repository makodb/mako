This is a historical status document.  The `Marshallable` abstract
base and the `MarshallDeputy` envelope were later retired;
production persistence code now serializes through `janus::Command`
(`SerializableEnvelope<MakoCommands>`) which produces byte-for-byte
identical wire bytes to the prior `MarshallDeputy` path.  Where this
doc says "wrap in MarshallDeputy" / "Marshallable kind", read "wrap
in Command" / "Command kind"; the underlying logic and
`[v32 kind][payload]` on-disk format are unchanged.

0b. FIX: KILL TIMEOUT FOR STALE COROUTINE RACE (2026-01-11)
    Problem: Occasional segfault during restart caused by stale election timer coroutine.

    Root cause:
    - Election timer coroutine sleeps for 200-400ms (HEARTBEAT_INTERVAL * 2-4)
    - Kill() only waited 100ms before deleting the server
    - Stale coroutine wakes up after server deleted -> use-after-free -> segfault

    Solution: Increased Kill() wait time from 100ms to 450ms.
    This ensures all sleeping coroutines have time to wake up, check stop_=true,
    and exit cleanly before memory is freed.

    Trade-off: Each Kill() call now takes ~450ms instead of ~100ms, slowing down
    tests with many kill/restart cycles. But eliminates the race condition.

    File changed:
    - src/deptran/raft/testconf.cc:544-546: usleep(100000) -> usleep(450000)

1. NOTIFYRESTART MECHANISM WITH STATUS TRACKING
   Implemented a robust NotifyRestart mechanism for multi-server crash recovery:

   - Added NotifyRestartStatus enum: ACKNOWLEDGED, DOWN, PENDING
   - Status tracking map in RaftCommo for each peer
   - Status update rules:
     * RPC succeeds, acknowledged=true  -> ACKNOWLEDGED (peer reconnected)
     * RPC succeeds, acknowledged=false -> DOWN (peer is down, will reconnect when it restarts)
     * RPC fails (timeout/error)        -> PENDING (should retry)

   - Assumes FAIL-STOP model:
     * Can confirm DOWN (peer responds with nullptr server)
     * Cannot confirm ALIVE (timeout could be partition or crash)
     * Crashed servers eventually restart with fresh connections

   See NOTIFY_RESTART_MECHANISM.txt for full documentation.

2. NOTIFYRESTART AUTOMATIC RETRY (2026-01-10)
   Added retry mechanism for PENDING peers in RaftServer::StartElectionTimer():
   - Checks for PENDING peers every 200-400ms
   - Retries NotifyRestart RPC until ACKNOWLEDGED or DOWN
   - Handles partition+restart scenario where partitioned server misses NotifyRestart

   Implementation in server.cc:
     auto c = commo();
     if (c != nullptr && c->HasPendingNotifyRestart()) {
       c->RetryPendingNotifyRestart();
     }

IMPLEMENTED FIXES

FIX 1: owns_poll_thread_ FLAG (Implemented 2026-01-06)
------------------------------------------------------
Problem: When Kill() destroys the old RaftFrame/Communicator, the destructor was
calling shutdown() on the poll thread. But this poll thread is SHARED with the
RPC server (for accepting inbound connections). Shutting it down kills the
server's ability to accept new connections.

Solution: Added owns_poll_thread_ flag to Communicator:
- Set to TRUE when Communicator creates its own poll thread (rusty::None passed in)
- Set to FALSE when poll thread is passed in (shared with RPC server)
- Destructor only calls shutdown() if owns_poll_thread_ == true

Files changed:
- src/deptran/communicator.h:378 - Added owns_poll_thread_ field
- src/deptran/communicator.cc:64-69 - Set flag in constructor, check in destructor


FIX 2: POLL THREAD REUSE AFTER RESTART (Implemented 2026-01-08)
----------------------------------------------------------------
Problem: After Restart(), there was a critical thread-safety issue:
- Inbound RPCs (via RPC server): Used ORIGINAL poll thread (from ServerWorker)
- Outbound RPCs (new Commo): Used NEW poll thread (created with rusty::None)
- RaftServer was accessed by TWO threads simultaneously
- This caused race conditions since RaftServer has no mutexes on most fields

The problem had TWO parts:

PART 1: The new Commo was creating its own poll thread instead of reusing
the original one. This was fixed by storing the poll thread in RaftServiceImpl
(which survives Kill) and retrieving it during Restart.

PART 2: Even with the correct poll thread, HeartbeatLoop and ElectionTimer
coroutines were being scheduled on the WRONG thread. The code was using
Coroutine::CreateRun() which schedules on the CURRENT reactor (site 0's test
thread), not on the server's poll thread.

Solution (Part 1 - Poll Thread Storage):
1. RaftServiceImpl now stores the poll thread during construction:
   - service.h: Added poll_thread_ field (rusty::Option<rusty::Arc<srpc::PollThread>>)
   - service.cc: Constructor accepts and stores poll thread
   - service.cc: Added GetPollThread(site_id) static method to retrieve it

2. Frame::CreateRpcServices passes poll thread to RaftServiceImpl:
   - frame.cc: Changed to pass poll_thread_worker.clone() to constructor

3. testconf.cc::Restart() retrieves the original poll thread:
   - Calls RaftServiceImpl::GetPollThread(svr) to get the stored poll thread
   - Passes it to new RaftCommo instead of rusty::None

Solution (Part 2 - Correct Coroutine Scheduling):
The old code in Restart() was:
  Coroutine::CreateRun([frame](){ frame->svr_->HeartbeatLoop(); });

This schedules on the CURRENT reactor (test thread), not the server's poll thread.

Fixed by using poll_thread->add() to schedule on the correct thread:
  auto& poll_thread = frame->commo_->rpc_poll_.as_ref().unwrap();
  auto hb_job = rusty::Arc<OneTimeJob>::new_(OneTimeJob([frame]() {
    Coroutine::CreateRun([frame]() { frame->svr_->HeartbeatLoop(); });
  }));
  poll_thread->add(rusty::Arc<Job>(hb_job));

Files changed:
- src/deptran/raft/service.h:34-44 - Added poll_thread_ field and GetPollThread()
- src/deptran/raft/service.cc:19-63 - Constructor stores poll thread, GetPollThread impl
- src/deptran/raft/frame.cc:200-202 - Pass poll thread to RaftServiceImpl
- src/deptran/raft/testconf.cc:610-696 - Retrieve poll thread and schedule on correct thread

Architecture after Fix 2:
  Before restart:
    Inbound RPCs  --> Original Poll Thread --> RaftServer (site 0)
    Outbound RPCs --> Original Poll Thread --/

  After Kill:
    Inbound RPCs  --> Original Poll Thread --> nullptr (atomic)
    RaftFrame/Server/Commo: DELETED
    RaftServiceImpl: SURVIVES (owned by RPC server, stores poll thread)

  After Restart:
    Inbound RPCs  --> Original Poll Thread --> NEW RaftServer (site 0)
    Outbound RPCs --> Original Poll Thread --/   (SAME thread! No race!)

  After restart:  [FIX2-OUTBOUND] HeartbeatLoop started site=0 thread=139662802810432
  Same thread ID = Fix 2 working correctly!


FIX 3: LOG_ FIELD PERSISTENCE (Implemented 2026-01-08)
------------------------------------------------------
Problem: After restart, servers were skipping log application with error:
  "[APPLY-LOGS] site=4 SKIP index=1 (no instance or log)"

Root cause: The RaftData serialization in raft_persistence.cc was only persisting
primitive fields (term, ballot, slot_id, etc.) but NOT the polymorphic
log_ command field.  The comment in the code at the time said:
  "// command pointers left as nullptr for now"

This meant restarted servers had log entries with empty commands, so they
couldn't apply the logs even though the metadata was correctly restored.

Solution: Modified SerializeRaftData and DeserializeRaftData to handle the log_
field via the polymorphic kind-tagged envelope (originally MarshallDeputy;
the post-L10f-2 equivalent is `janus::Command`):

SerializeRaftData:
1. Use srpc::Marshal for serialization (instead of raw memcpy)
2. Write primitive fields
3. Write has_log flag (uint8_t) indicating if log_ is present
4. If present, wrap log_ in the kind-tagged envelope and serialize it
   - Envelope writes kind_ (type ID) then calls save()

DeserializeRaftData:
1. Use srpc::Marshal for deserialization
2. Read primitive fields
3. Read has_log flag
4. If present, construct the kind-tagged envelope and deserialize
   - Envelope reads kind_, uses factory to create correct type, calls load()
5. Assign the recovered payload to entry.log_

Files changed:
- src/deptran/raft/raft_persistence.cc:154-213 - Rewrote Serialize/Deserialize functions

KNOWN ISSUE: NOTIFYRESTART WAS FIRE-AND-FORGET (NOW FIXED)
----------------------------------------------------------
Previous issue (now resolved):
- Restarted server sent NotifyRestart ONCE to all peers
- If a peer was partitioned, it never received the notification
- When partition healed, peer had stale connection to restarted server

SOLUTION IMPLEMENTED (2026-01-10):
Added automatic retry mechanism in RaftServer::StartElectionTimer():
- Election timer loop checks for PENDING peers every 200-400ms
- Calls commo()->RetryPendingNotifyRestart() if any PENDING peers exist
- Retries until peer responds (ACKNOWLEDGED) or is confirmed down (DOWN)

This handles the partition+restart scenario:
1. Server A is partitioned
2. Server B restarts, sends NotifyRestart (A is PENDING)
3. B's election timer retries every 200-400ms
4. A's partition heals
5. A receives NotifyRestart, reconnects to B
6. Stale connection fixed!

Tests 16-18 verify this mechanism works correctly.
