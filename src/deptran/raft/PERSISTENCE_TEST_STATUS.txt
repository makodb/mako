FIX 1 IMPLEMENTED: owns_poll_thread_ FLAG
------------------------------------------
Problem: When Kill() destroys the old RaftFrame/Communicator, the destructor was
calling shutdown() on the poll thread. But this poll thread is SHARED with the
RPC server (for accepting inbound connections). Shutting it down kills the
server's ability to accept new connections.

Fix: Added owns_poll_thread_ flag to Communicator:
- Set to TRUE when Communicator creates its own poll thread (rusty::None passed in)
- Set to FALSE when poll thread is passed in (shared with RPC server)
- Destructor only calls shutdown() if owns_poll_thread_ == true

Files changed:
- src/deptran/communicator.h: Added owns_poll_thread_ field
- src/deptran/communicator.cc: Set flag in constructor, check in destructor


KNOWN ISSUE: INBOUND/OUTBOUND POLL THREAD MISMATCH (CRITICAL)
-------------------------------------------------------------
After Restart(), the architecture is:
- Inbound RPCs (RPC server): Uses ORIGINAL poll thread (from ServerWorker)
- Outbound RPCs (new Commo): Uses NEW poll thread (created with rusty::None)

This APPEARS to work but is actually UNSAFE due to race conditions.

Shared Memory (RaftServer) accessed by both threads:
- currentTerm, vote_for_, state_ (leader/follower/candidate)
- raft_logs_ (log entries)
- commitIndex, lastLogIndex, match_index_, next_index_

Access Patterns:
- Inbound (Poll Thread A): HandleAppendEntries() modifies currentTerm, raft_logs_, commitIndex
- Outbound (Poll Thread B): HeartbeatLoop() reads currentTerm, match_index_; callbacks modify match_index_

Why this is UNSAFE:
- Original design assumed ONE poll thread = all coroutines run cooperatively (no preemption)
- With TWO poll threads running simultaneously, we have TRUE CONCURRENT ACCESS
- RaftServer was NOT designed for multi-threaded access (no mutexes on most fields)
- Potential race conditions:
  1. Thread A modifying currentTerm while Thread B reads it
  2. Thread A appending to raft_logs_ while Thread B iterates it
  3. Both threads modifying match_index_ simultaneously

Current "working" behavior is LUCK - we haven't hit a race condition yet in simple tests.

FIX 2 (NOT YET IMPLEMENTED - ESSENTIAL FOR CORRECTNESS):
- Pass server's poll thread to new commo in Restart()
- Requires accessing ServerWorker's svr_poll_thread_worker_ from testconf.cc
- Need to add registry or lookup mechanism since svr_workers_g is static in s_main.cc
- This restores single-threaded cooperative coroutine model = no races


KNOWN ISSUE: NOTIFYRESTART IS FIRE-AND-FORGET
----------------------------------------------
Current NotifyRestart mechanism is imperfect:
- Restarted server sends NotifyRestart ONCE to all peers
- If a peer is also down at that moment, it never receives the notification
- When that peer comes back up, it still has stale connection to the first server

Example scenario:
1. Server A and Server B are both killed
2. Server A restarts, sends NotifyRestart to all (B is down, doesn't receive)
3. Server B restarts, sends NotifyRestart to all (A receives, reconnects to B)
4. But A never told B to reconnect, so B still has stale connection to A

FIX 3 (NOT YET IMPLEMENTED):
- Track which peers have acknowledged NotifyRestart
- Periodically retry NotifyRestart to unacknowledged peers
- Use large retry interval (e.g., 5-10 seconds) to minimize CPU overhead
- Stop retrying once acknowledged or after max attempts
